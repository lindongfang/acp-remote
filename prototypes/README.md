# PWA 设计原型

`acp-remote-pwa.html` 是 **ACP Remote Web/PWA 的设计原型**，用来在写实现之前把页面结构、状态与交互对齐。

## 它是什么

- 单文件 HTML，零外部资源（无 CDN、无字体、无图片），符合 `FRONTEND_DESIGN.md §4.5` 的 CSP 基线
- 用 hash 路由在四个页面之间切换，用右下角「原型控制台」切换各种状态与场景
- 数据是写死的假数据，**不连任何真实服务**

```text
#/pair            配对页（13 个状态：网页入口输入 8 位 Crockford 配对码（XXXX-XXXX），S0 只显示静态有效期提示，lookup 后才显示倒计时；二维码入口保留原流程；通过进目录，失败只显示原因）
#/dirs            目录页（目录为主角：搜索 + 状态筛选，卡片含同名路径尾段、计数与徽标、⊕ 新建、查看全部）
#/dir/<id>        目录详情（页头：次级「目录」按钮 + 目录名 + 会话数 + 路径，按时间倒序平铺，每页 10 条 + 页码翻页）
#/chat/<session>  对话页（左：同目录会话 + 目录内搜索 / 中：时间线 + 输入区 / 右：变更文件 + 结构化差异行）
```

四个页面与共享外壳（顶栏、开发模式横幅、帮助抽屉、toast、主题三态）的结构都已按本原型落进 `clients/app`
（主机面板的若干信息仍在补齐，逐条见缺口清单）；配对页在**实现**里仍按「打开 URL 即配对」工作——地址片段是唯一入口，
读到后立即清除；`/pair` 的 sync 载荷自动开始认领，`/node-link/pair` 的 node-link 载荷只呈现对端信息、不发请求。
配对中显示真实剩余有效期，通过后自动进目录（路由 `/`），失败只给固定原因。实现不绘制页头/返回，也不提供页内主题切换
（这是对移动原型配对页「标题栏 + 主题按钮」的有意偏离）。**桌面原型现在按 `openspec/changes/pairing-code-web-entry/`
画了「`/pair` 无 fragment 时输入 8 位 Crockford 配对码」的入口，S0 不显示数字倒计时**；移动原型仍保留配对码入口
（与「移动端只使用二维码」的产品决策不一致，属于原型遗留）。实现尚未跟进，产品文档也还没写回
（见下文「配对页的 8 位配对码」）。本文件记录原型与「实现/权威文档」的关系，
缺口清单见 [`IMPLEMENTATION-GAPS.md`](./IMPLEMENTATION-GAPS.md)。

## 它不是什么

- **不是产品代码**，不参与构建、不被任何 crate 打包，也没有测试
- **不是权威文档**。产品行为、协议语义与安全模型以 `docs/` 为准；`FRONTEND_DESIGN.md §9` 第 1 条把本原型登记为**交互口径来源**，但它本身不定义契约
- 原型里的 mock 数据、时间、指纹、会话标题都是编造的
- 原型自带的「原型控制台」（右下角）**不是产品 UI**，不移植；它是评审时切换状态用的，其中的
  `A.canCreate` 一类开关只是模拟分支，不代表产品有权限门控（设备方向没有授权维度）

## 原型结论的同步现状

本节原先是一张「已知与权威文档的差距（实施前必须先解决）」表：原型当时画着、而合同与实现还没有的能力。
2026-10-17 复核：**那张表里的每一项都已闭合**，结论也写回了权威文档。逐项记录落地位置，供后继改动核对
（本表只记「原型结论落到哪里」，具体缺口见 [`IMPLEMENTATION-GAPS.md`](./IMPLEMENTATION-GAPS.md)）。

| 原差距项 | 现状 | 落地位置与依据 |
|---|---|---|
| 目录字段（`SessionSummary` 没有 workspace 概念） | **已闭合** | `schemas/sync/v1/common.schema.json` 的 `sessionSummary.workspace`（feature `core.local-catalog.v1`）；`SYNC_PROTOCOL.md §9.4` |
| 设备侧创建会话（Sync v1 只有 Node Link 有 `session.create`） | **已闭合** | `session.create` 的 transport 扩为 `["sync","node_link"]`（`compatibility/commands/v1/commands.json`），feature `core.session-create.v1`；`SYNC_PROTOCOL.md §11.5` |
| Agent 列表查询（PWA 无从得知本机配置了哪些 Agent） | **已闭合，且不需要新命令** | Agent 目录随快照下发（feature `core.local-catalog.v1`；`SYNC_PROTOCOL.md §9.4` 的 `agents` 资源），主机面板与创建弹层的选择器都由它供数 |
| 目录路径下发（与「不得经 wire 传输路径」冲突，待决定） | **已闭合，口径已改写** | feature `core.workspace-path.v1`（快照 `workspaces` 条目的可选 `path`）与 `core.workspace-browse.v1`（查询命令 `workspace.browse`）；路径的可见面收敛为「只有这两处、且都受 feature 门控」，见 `SYNC_PROTOCOL.md §9.4/§11.5` 与 `SECURITY_DESIGN.md §12.3` |
| 目录别名不再出现在界面上 | **已闭合** | 别名只作路由与命令引用的内部标识，界面不呈现它；同名目录用服务端下发的路径尾段消歧（`FRONTEND_DESIGN.md §4.1`） |
| 顶部「新建」：浏览节点目录并在需要时新建目录 | **已闭合** | `workspace.browse`（逐层列举：名称 + 绝对路径 + 是否已登记 + `truncated`）与 `session.create` 的显式开关 `createIfMissing`；未登记目录下新建的会话不归属任何目录项（客户端不造「未分组」分组） |
| 移动端布局（只有桌面版） | **已闭合，带一处登记的有意偏离** | 实现是一个响应式应用：宽屏用原型的多栏形态，窄屏收成单列 + 二级视图切换（`pwa-prototype-parity`）；**保留 720px 断点**而不删断点，理由与另外三处偏离一起登记在该变更 `proposal.md` 的「四处**有意偏离**」表 |

那四处有意偏离（不是遗漏）是：响应式断点、来源与同步时刻标注的位置、Agent 连接状态缺席时呈现「状态未知」、
授权按钮文字色的取色方式。它们的取舍理由以 `openspec/changes/pwa-prototype-parity/proposal.md` 为准。

## 修改原型时的注意事项

浏览器"打开是空白"多数是**运行期**错误，`node --check` 只查语法。改动后至少确认：

1. 每条路由都能打开
2. 控制台里的每个下拉/开关都能切换
3. 抽屉、弹层的关闭路径（`Esc` / 点外部 / 关闭按钮）

如果条件允许，用最小 DOM 桩在 Node 里跑一遍脚本，比肉眼可靠。

## 移动端原型

`acp-remote-pwa-mobile.html` 是同一套设计的移动端形态，在手机上打开，或在桌面打开（自动画成 430×92vh 的手机画布）。

```text
#/pair             配对页（13 个状态：网页入口输入 8 位 Crockford 配对码（XXXX-XXXX），S0 只显示静态有效期提示，lookup 后才显示倒计时；二维码入口保留原流程；通过进目录，失败只显示原因）
#/dirs             目录页（首页，顶部 ⋯ 打开主机面板）
#/dir/<id>         目录详情（按时间倒序 + 每页 10 条 + 翻页 + 新建会话）
#/chat/<id>        对话页
#/sessions         同目录会话列表（从对话页 ☰ push 进来；目录内搜索，不分页）
```

### 与桌面端的关系

**实现时是一个响应式应用，不是两个应用。** 两者的导航模型不同，所以交互结构也不同：

| | 桌面 | 移动 |
|---|---|---|
| 变更文件 | 右栏常驻 | 底部 tab 的**同级视图**（不是抽屉） |
| 会话切换 | 左栏常驻 | 标题旁 `☰` → push 一页 |
| 诊断 / 主机面板 | 右侧滑出 440px | **底部全屏 sheet** |
| 模型/模式/上下文 | 右对齐一行 | 一行可横滑 chips（44px 触达） |
| 权限按钮 | 横排三个 | 两列网格，`允许一次` 跨满整行 |
| 触达尺寸 | 44px | 会话行 56px |
| 安全区 | — | `env(safe-area-inset-*)` |

**Markdown 渲染、语法高亮、折叠块、降级卡片、诊断抽屉、主机面板、连接状态机、命令与状态判定逻辑，两端完全一致。**

`[实现现状]`（2026-10-17）落地的是**桌面那一列的结构 + 一套 720px 断点**：窄屏把左栏与右栏降为可切换的
次级视图（`all` / `timeline` / `sessions` / `files`，四列内容始终在 DOM）。上表「移动」那一列**自己的导航
形态**（底部 tab、`☰` push 页、底部全屏 sheet、56px 会话行）**没有实现**——这是 `pwa-prototype-parity` 登记
的有意偏离（保留断点而不是删断点，理由是 `FRONTEND_DESIGN.md §4.1/§9` 把响应式手机布局列为必须实现与验收项），
不是「实现落后于原型」。

下面这两个差异是**原型文件内部**的差异（移动端对照桌面端缺的陈列态），不是实现的缺口：

- 无权限设备的「不显示新建入口」态（桌面端有）——这一态已随设备权限层一起删除（`pairing-model`：
  设备方向没有授权维度，`FRONTEND_DESIGN.md §2.2/§9` 明确要求入口不按权限门控），因此它在两端都
  **不再是产品行为**；桌面原型里的那一档只由控制台的 `canCreate` 开关模拟
- `#/sessions` 那条 push 页没有分页与「已显示 N / M + 加载更多」（桌面端左栏有），移动端 mock 数据少，
  暂不需要；详情页的分页两端都有（每页 10 条 + 页码翻页）

#### 配对页的 8 位配对码

桌面原型按 `openspec/changes/pairing-code-web-entry/` 画了配对码入口；移动原型也画了，两者在 S0 的倒计时行为上已经一致。移动原型仍保留配对码入口这一点与产品决策不一致（移动端只使用二维码），属于**原型遗留**：

- **桌面原型**（`acp-remote-pwa.html`）：`/pair` 没有 fragment 时显示配对码输入。配对码是 8 位 Crockford 字母数字，终端显示为 `XXXX-XXXX`；输入不区分大小写，`I`/`L` 归一化为 `1`、`O` 归一化为 `0`，允许粘贴带一个短横线的整段码。**S0 不显示数字倒计时**，只显示静态提示“配对码 5 分钟内有效”；lookup 成功后才开始显示倒计时。提交后依次经过「正在核对配对码（lookup）」→「正在认领（claim）」→「配对中（等待电脑确认）」→ 审批通过后自动进目录，**lookup/claim 不重置剩余时间**。失败面新增固定呈现「配对码不对或已过期，请重新生成配对码」，**页内不提供重试按钮**，恢复路径是回电脑重新 `device pair`。控制台的…
- **移动原型**（`acp-remote-pwa-mobile.html`）：配对码卡片、来源胶囊、S0 静态提示与固定失败文案已与桌面一致；**S0 不显示数字倒计时**，lookup 成功后才开始倒计时。手机上一行放 4 格、两行放 8 格。**注意**：`pairing-code-web-entry` 的已确认决策是「移动端只使用二维码，不提供输码入口」；移动原型的这一块是**原型层面的遗留不一致**，本次只同步了行为与文案，没有回退入口。若要让移动原型与产品决策一致，需要单独把这一块改回二维码入口。
- **实现**（`clients/app`）：仍只接受地址片段，与 `FRONTEND_DESIGN.md` / `SYNC_PROTOCOL.md` 当前的「地址片段是唯一入口」一致。原型的配对码入口目前**只是评审用原型**；`pairing-code-web-entry` 尚未实现，权威文档也尚未写回。落地时需要先完成 lookup 端点、配对码派生与内存查找、限流/失败失效、前端 `awaiting_code` / `looking_up` / `code_invalid` 阶段，不能只照原型加一个输入框。

两端原型的倒计时都从 **lookup 成功后**开始；S0 不显示数字倒计时，只显示静态提示，因为页面打开时并不知道配对已经生成了多久。真实实现同样在 lookup 后使用响应里的 `expiresAt`。

二维码入口原有的失败面与行为没有改动（地址过期、已被使用、无法识别、来源不一致、需要 HTTPS、请求失败），审批通过后仍约 1.6 秒自动进目录，`/node-link/pair` 仍不发起 claim/status，页内仍不提供主题切换。SAS 短验证码与设备权限清单早已从产品里删除（`pairing-model`），两端原型也不再呈现它们。

### `.build/`：移动端的拼装源文件

`acp-remote-pwa-mobile.html` 是**生成物**，不要直接改它。要改移动端，改这三个文件后重新拼装：

```text
prototypes/.build/
├─ m-head.html   CSS + HTML 骨架 + 数据与状态
├─ reuse.js      从桌面原型抽出的纯逻辑函数（Markdown/高亮/折叠/降级/主机面板）
├─ m-tail.js     移动端视图、路由、交互
└─ assemble.mjs  拼装脚本
node prototypes/.build/assemble.mjs
```

`reuse.js` 是用一次性脚本从 `acp-remote-pwa.html` 抽出来的。桌面端改了某个复用函数后，需要重新抽取再拼装；**当前没有自动同步**，改了桌面端记得手动核对 `reuse.js`。

同目录下另有 `density.mjs` 与 `sync-theme.mjs` 两个**一次性脚本**（那一轮评审时对 `m-head.html`/`m-tail.js`
做批量替换用），它们**不在拼装链上**：拼装只读上面那三个文件。

### 主题

默认**跟随系统**（`prefers-color-scheme`）。两个原型顶部都有一个 🌙/☀️ 按钮，点一次切到另一种并持久化；控制台的下拉多一个「跟随系统」选项用于复位。

产品形态现在是**三态**（跟随系统 / 白天 / 黑夜，选择持久化为客户端 UI 偏好），已由 `pwa-prototype-parity`
落地到 `clients/app`（`FRONTEND_DESIGN.md §4.1`）：**跟随系统是缺省值**，显式选白天/黑夜是用户覆盖；因此
「原型里的手动切换只是评审覆盖项」这一条已经过时——今天它是一条正式的产品行为。

深浅色通过 `data-theme` 属性驱动，`<head>` 里有独立小脚本先于首次绘制设置，避免深色用户看到一帧白屏。

主题图标定为**实心 SVG、语义=点击后的效果、颜色=亮橙**（白天 `#d9480f` / 黑夜 `#ffa94d`，由 `data-ic="orange"` + CSS 按主题给出，不用内联颜色）。两个原端的图形路径常量与写法完全一致。

配色原本给过 8 档与 6 种图形样式做对比，已按评审结论固定，控制台里对应的下拉与分支代码都删掉了。
