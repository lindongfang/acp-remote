# Design

## Context

动机与用户确认要求见 [proposal.md](proposal.md)，行为规则见 `specs/backup-recovery/spec.md` 与 `openspec/specs/` 长期规格。本变更当前处于需求与设计定义态，具体施工工作包与验收用例在正式开工时基于真实代码树建立。

## Goals / Non-Goals

**Goals:**
- 核心平台配置与管理事实、原生数据分别建立一致性备份并校验各自完整性。
- 支持只到隔离新目标的恢复验证，确保旧请求代际、运行期单会话控制权、旧信任与未决审批不静默复活。

**Non-Goals:**
- 将独立展示快照库（`session-transcript-cache`）或实时内存缓存纳入平台备份，或从展示快照伪造恢复模型上下文；覆盖原位运行中的用户数据库、密钥或原生存储。

## Decisions

### 1. 职责、双轨隔离与权威

平台备份只涵盖核心配置及控制面 SQLite 中允许备份的管理事实，**显式排除物理隔离的展示快照库（`session-transcript-cache`）、临时内容缓存、运行期内存控制状态与认证私钥**；原生会话、历史和模型上下文属于独立的原生组件，绝不因核心管理库备份成功或存在展示快照而声称原生上下文已备份。

### 2. 来源能力与接口

核心控制面管理库用一致性快照（如 SQLite 一致性备份 API）与清单摘要校验，天然不受展示快照库大体积 I/O 干扰。原生组件只使用经验证的一致性导出/备份或静止复制路径；无法排除外部并发写入时不声明一致性备份成功。

### 3. 状态与失败

恢复只写入隔离新目标，按规格“隔离恢复与校验”逐项核对清单声明包含的组件。平台组件校验版本、摘要及内部管理关联；平台管理记录指向未备份原生对象时，保留不可执行、当前不可解析的引用，不为校验而连接实际原生存储。声明包含的原生组件缺失或损坏时报告分项失败及清单范围整体失败，不删改清单降为平台包。不自动生成密钥、激活旧客户端信任、恢复单会话控制权或复活旧审批，不启动外部工具。

### 4. 资源与安全

旧命令的签发期限、去重结果、节点请求代际和过期拒绝水位可作为不可执行历史元数据恢复，但不能据较早备份推导原请求在当前仍有执行资格。新目标获授权启用时建立独立的新节点请求代际，所有会话控制权保持未接管初始状态，旧请求直接拒绝；正常重启使用原完整管理库时继续保留原期限和去重事实。

## Risks / Trade-offs

- [各 Harness 原生一致性备份能力差异] → 逐款核实静止或导出条件，未证实前仅开放核心平台管理组件备份，不虚报全量备份。
- [无密钥副本误启动风险] → 不含身份密钥的隔离恢复副本仅支持离线检验，启用新节点实例须显式初始化新身份与授权。

## Migration Plan

开工前盘点当时核心控制面全部持久化管理表结构与迁移版本，确保备份清单版本与核心 SQLite schema 演进严格绑定（独立于展示快照库文件），不修改或删除用户现有数据。
