# Design

## Context

动机与用户确认要求见 [proposal.md](proposal.md)，行为规则见 `specs/backup-recovery/spec.md` 与 `openspec/specs/` 长期规格。本变更当前处于需求与设计定义态，具体施工工作包与验收用例在正式开工时基于真实代码树建立。

## Goals / Non-Goals

**Goals:**
- 平台配置与管理事实、原生数据分别建立一致性备份并校验各自完整性。
- 支持只到隔离新目标的恢复验证，确保旧请求代际、旧信任与未决审批不静默复活。

**Non-Goals:**
- 从平台备份恢复聊天正文或实时缓存；覆盖原位运行中的用户数据库、密钥或原生存储。

## Decisions

### 1. 职责与权威

平台备份只涵盖配置及允许备份的管理事实，排除聊天缓存与认证密钥；原生会话、历史和上下文属于独立组件，不因平台备份成功而承诺原生上下文可恢复。

### 2. 来源能力与接口

平台管理库用一致性快照（如 SQLite 一致性备份 API）与清单摘要校验。原生组件只使用经验证的一致性导出/备份或静止复制路径；无法排除外部并发写入时不声明一致性备份成功。

### 3. 状态与失败

恢复只写入隔离新目标，按规格“隔离恢复与校验”逐项核对清单声明包含的组件。平台组件校验版本、摘要及内部管理关联；平台管理记录指向未备份原生对象时，保留不可执行、当前不可解析的引用，不为校验而连接实际原生存储。声明包含的原生组件缺失或损坏时报告分项失败及清单范围整体失败，不删改清单降为平台包。不自动生成密钥、激活旧客户端信任或旧审批，不启动外部工具。

### 4. 资源与安全

旧命令的签发期限、去重结果、节点请求代际和过期拒绝水位可作为不可执行历史元数据恢复，但不能据较早备份推导原请求在当前仍有执行资格。新目标获授权启用时建立独立的新节点请求代际，旧请求直接拒绝；正常重启使用原完整管理库时继续保留原期限和去重事实。

## Risks / Trade-offs

- [各 Harness 原生一致性备份能力差异] → 逐款核实静止或导出条件，未证实前仅开放平台管理组件备份，不虚报全量备份。
- [无密钥副本误启动风险] → 不含身份密钥的隔离恢复副本仅支持离线检验，启用新节点实例须显式初始化新身份与授权。

## Migration Plan

开工前盘点当时全部持久化管理表结构与迁移版本，确保备份清单版本与 SQLite schema 演进严格绑定，不修改或删除用户现有数据。
