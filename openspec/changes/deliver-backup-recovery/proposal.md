# 交付一致性备份与恢复验证

## Why

节点接入与通用会话闭环已交付，一致性备份与隔离恢复验证尚未实现。为按重设计建立可独立验收的交付闭环，需要支持核心平台管理数据与原生数据分组件一致性备份及隔离恢复校验，并显式排除独立的受管展示快照库（`session-transcript-cache`）与运行期内存控制状态（`session-control-takeover`）。

## Success Criteria

### 用户原始要求

> acp-remote还是不保存会话数据，以harness 数据为准
> 只提供原生删除，不保留隐藏功能。
> 查看时允许激活进程，不限制只读；查看本身不发送新输入或批准工具。

- **R2-003 确认**：较早备份中的旧请求期限、代际和过期水位在隔离恢复中只作不可执行历史元数据，不能变成新目标的执行资格；正常重启与隔离恢复分别处理。
- **SR-005 确认**：按备份清单声明包含的组件判断恢复成功；仅平台包无需连接原生存储，已声明但缺失或损坏的原生组件使清单范围整体失败，不静默降级。
- **CT-001 / TC-001 对齐（2026-11-19）**：物理隔离的展示快照库（默认 30 天滑动保留、10 GiB 上限）与临时上传/内存视图一律排除在核心平台管理备份之外，绝不把展示快照导出冒充原生会话或上下文备份；单会话客户端控制权（`SessionControlState`）属运行期易失状态，不在备份或恢复中保存或复活。

### 硬约束与非目标

- 以[重设计 §5.1、§8、§10.1](../../../docs/HARNESS_CONTROL_PLANE_REDESIGN.md)与 `openspec/specs/` 长期规格为依据；采用新架构、不兼容旧系统。
- 不得以复制正在写入的文件或打包展示快照库冒充原生一致性备份；不得覆盖用户实际数据库、密钥和原生存储进行验收。
- 首期限定 Windows 节点 + Web，App 后续；当前处于需求与设计定义阶段，`tests/plan/tasks` 在正式启动本变更时基于真实代码树生成。

### 本 change 的成功判据

- SC1：平台核心配置与管理事实、原生数据分别备份并证明各自一致性；平台备份不恢复聊天或模型上下文，独立展示快照库与临时缓存不入历史备份。
- SC2：隔离恢复按清单逐项校验，旧请求资格、运行期控制权、旧客户端信任或旧审批均不可在新目标静默复活。
- SC3：正式开工时基于当前规格生成 `tests/plan/tasks` 并通过编码前门禁、真实实现与集成交付验收。

## What Changes

- 提供平台核心配置/管理事实（控制面 SQLite）与原生数据的分组件一致性备份及清单摘要校验；独立展示快照库（`session-transcript-cache`）、内存缓存与认证私钥不入历史备份。
- 实现到隔离新目标的恢复校验，区分平台-only 恢复与含原生组件恢复，隔离旧节点请求代际并保持单会话控制权初始归零。

## Exploration

- **隔离恢复与请求代际（R2-003 / CT-001）**：隔离恢复中的旧请求资格只作历史元数据；另获授权启用新目标时建立独立的新节点请求代际，且所有会话客户端控制权初始处于未接管归零状态，不复制原节点密钥或回退水位重放命令。正常重启继续保留原完整去重事实（引用 `session-execution`）。
- **按清单判定恢复结果（SR-005）**：仅平台包恢复成功时明确说明历史和模型上下文未恢复；清单声明包含的原生组件缺失或损坏时报告分项失败及整体失败，不删改清单伪装成纯平台包。
- **双轨存储隔离与原生权威（Q-001 / TC-001）**：模型上下文与原生历史以 Harness 为准；核心平台包仅导出控制面 SQLite 管理事实，物理隔离的展示快照库不纳入平台备份，避免备份膨胀或误导用户以为已备份可恢复模型上下文。
- **术语与 ADR 复核**：复用 [领域术语表](../../GLOSSARY.md) 中展示快照库、会话控制权接管与管理事实定义，无新增独立 ADR。
