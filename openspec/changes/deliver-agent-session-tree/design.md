# Design

## Context

动机与用户确认要求见 [proposal.md](proposal.md)，行为规则见 `specs/agent-session-tree/spec.md` 与 `openspec/specs/` 长期规格。本变更当前处于需求与设计定义态，具体施工工作包与验收用例在正式开工时基于真实代码树建立。

## Goals / Non-Goals

**Goals:**
- 从原生可靠身份、父子关系和委派建立可重建视图，在父步骤内展开可读子历史（父倒序、子正序、默认 10 轮）。
- 原生读取、运行与平台管理存储职责分离，子目标实际加载纳入主树容量管理。

**Non-Goals:**
- 持久保存子会话正文或关系档案；引入未经授权的厂商私有文件读取器。

## Decisions

### 1. 职责与权威

主接入按通用逐能力规则可用，关系展示及子历史展开各自判断；分页遵循 `history-navigation`，结构及当前连接视图遵循 `structured-history`。缺少子历史读取只限制对应展开，不使整个接入不可用。参与者、会话及委派以原生可验证身份及关系为权威，平台只保留可失效、可重建的视图。

### 2. 来源能力与接口

关系校验原生范围、无环和目标权限；同一子身份多次委派保留不同来源步骤，不按名字或时间合并。无法证明独立子历史则保留当前原生工具结构并说明限制。

### 3. 状态与失败

父步骤内按需展开，子正序、父倒序、默认 10 轮，嵌套逐层请求。每次重开及节点重启重新校验原生关系，原生缺历史时不伪造永久子档案。

### 4. 资源与安全

原生关系变化使缓存关联失效，已删除父目标不由平台墓碑关系重建为原生事实；管理审计中的不透明目标引用与浏览关系分开。每层展开独立核对读取和分页能力；实际子目标加载遵循 `session-resource-policy` 的主树归属、名额及释放规则。根已删除或主树归属不明时仅使用无需加载且有权的查询，不从缓存猜测资源归属。

## Risks / Trade-offs

- [各 Harness 子关系暴露能力不一] → 按实际已接入 Harness 分别验证，缺原生关系或子历史时如实呈现限制，不承诺统一完整树。
- [跨层加载资源泄漏或误计数] → 严格走主树资源所有权端口，禁止绕过主会话容量账本直接激活子目标。

## Migration Plan

开工前盘点当时实际的 SQLite schema 与管理协议版本；本能力不建立永久聊天历史表，涉及管理元数据扩展时保证已有身份、信任、管理与原生数据无损保留。
