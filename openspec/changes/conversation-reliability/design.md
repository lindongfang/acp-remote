# Design

## Context

动机与批准范围见 proposal.md。已检查的实现显示：

- `core/src/broker.rs::submit_prompt_bound` 接受普通输入时提交轮次与命令事件，正文只在内存 QueuedTurn；首条的 `commit_first_submission` 已有完整保存能力，不能把它误当成所有输入都已保存。
- `features/conversation-timeline.ts` 对 sentPrompts 与所有历史用户正文按文本计数抵消；旧“继续”会抵消新“继续”。`SentPrompt` 只存在内存，无法解决刷新。
- `ConversationTimeline.tsx::TurnEntry` 隐藏正常进行中的轮次。思考、工具等已有专门组件，应保留，补齐真实的过程反馈。
- 草稿平台只有一个 sessionStorage 定位，复用查找却扫描 preparations 并限定 ready；应统一为一个准备槽位，不扩展成草稿列表。
- FRONTEND 与 SECURITY 文档仍混有主动离页删除、同目录复用等口径。现有 web-session-preparation 与 session-activation-lifecycle 尚有未完成验收；本变更不替它们勾选完成。
- 用户已有 compose.rs、.diagnostics/ 和 target-verify/ 修改/产物，不作为本次可覆盖范围。openspec/config.yaml 对客户端未实现的记录滞后于实际代码；规划以代码和权威文档为证，不把该旧描述视为阻止客户端工作的依据。

## Goals / Non-Goals

Goals：用 Owner 一次受理事务建立每条输入的权威正文；以已有 requestId、turnId、messageId 串起显示和回显；保留原始 ACP、已有层级依赖与单一临时会话。

Non-Goals：不扩大 Access 持久化白名单，不新增长期浏览器正式正文缓存，不修改签名/授权，不自动重发 uncertain，不恢复旧历史中从未保存的输入。

## Decisions

### D1 — 普通输入受理与正文同事务

扩展 owned 受理写集，使每个普通 prompt 在同一事务生成用户 messageId、保存完整内容、绑定附件、写 requestId/turnId 关联和已有幂等记录。失败时全回滚，提交后才发 accepted 和事件、派发 Agent。沿用首条的内容编码与语义，不为后续消息建立另一套文本格式；首条继续走已有原子转正事务。

为普通输入生成 Owner 来源用户消息事件，不伪造 ACP rawJson；原文可用性按协议允许的来源缺席规则表达。完整内容由 session.read 提供，首条与后续均覆盖，事件投影与读取只来自同一持久消息。具体读取路径必须写进 WP1 合同：`session.read` 的 `messages` 页从 `owned_message` 读取 `channel='user'` 的行并映射为 `role=user`，用户在会话中的顺序与分页按该持久行计算；`user.message.delta` 只用于实时可见性与未读回时的易失呈现，不作为长期正文来源，也不与同一 messageId 的持久行重复拼接。这样超过事件文本上限（262144 字符）的输入、事件过期或已压缩的历史仍能完整读回。不采用只加客户端缓存的方案，因为多端与刷新仍无权威数据。

### D2 — 稳定关联替代同文匹配

本地提交以 requestId 为键；受理结果/命令归属取得 turnId 后，只用该 turn 内的正式用户 messageId 接替它；首条沿用准备关联中的 firstMessageId。关系未确认时保留本地条目，绝不用旧历史文字抵消。普通提交扩展现有派发上下文与回显关联机制，携带本次已保存的消息/请求/轮次及内容摘要；只有上下文证明且完整内容一致才消除重复投影，分块不同或迟到不可归属时保留独立回显及 ACP 原文。

默认不新增 wire 字段：利用已有命令/轮次因果关系、消息 turnId/messageId 与首条关联。如果 WP1 合同审查发现其中任一边界不能可靠传递身份，必须在其冻结合同中显式补齐并版本协商，再允许下游实施，不能退回文本匹配。该情况须记录精确字段与共享 fixture，不得仅依靠页面推断。

### D3 — 过程状态与实际内容分开

feature 层把提交中、等待响应、会话恢复中、已知工具状态、失败归约为明确互斥阶段。优先显示实际工具/思考内容，只在无实际内容的阶段补一个紧凑过程行；恢复成功撤掉恢复提示。不会因为一段时间无输出就断言“思考中”，也不改变会话空闲/活跃/待处理主状态。

浏览器验收预算：点击有效提交到本地可见反馈不超过 100ms；当前前台普通负载下，客户端收到事件到 DOM 更新不超过 250ms。这是本次拟定验收预算，不是已测结论或网络服务承诺；分别记录 Agent 发出到 Owner 持久化、广播、浏览器接收、渲染各段耗时，报告样本数、最大值与第 95 百分位耗时，不把 Agent 启动/网络延迟混进渲染耗时。恢复开始即反馈，不设虚假百分比或自动重发。

### D4 — 一个准备槽位

槽位以 origin/Owner/设备/标签页隔离，内部持有一个 sessionId。普通导航只停止当前查看/续租，不作废槽位或草稿；刷新可在正式会话页、目录页启动后从非敏感定位恢复该唯一准备的展示索引，正文/凭据仍只经专用平台端口读取。新建入口无论原目录是否相同、准备是否 ready，优先导航回该槽位；分配在途也必须共用一个闸门。

明确换 Agent 通过现有 discard/release 顺序作废旧草稿和迟到写，获得新 ID 后替换槽位；证明的绑定不变。更换目录**不提供原位替换**：用户必须先显式放弃当前临时会话（确认后 `discard`/`release` 清理草稿与资源），再从新目录走普通新建并获得新 ID；任何普通新建入口都不得把现有槽位改绑到所点目录，否则旧证明会被静默用于新路径。接受后槽位退出临时角色，待正式输入读取确认再清草稿，后续显式新建可分配新 ID。复制标签页和其他身份不得接管原准备；资源租约到期使用证明同 ID restore，不能凭陌生 URL 创建。

### D5 — 原型核对与文档归属

以 `prototypes/acp-remote-pwa.html` 和 mobile 文件核对消息、折叠、工具、输入与窄屏切换，记录桌面/窄屏、明/暗主题差异；过程行采用现有主题 token。修正文档中隐藏所有进行中提示与离页删除的过时描述。新增规范是补充约束，实施 WP1 必须把现有冲突段落一并整理，不能并存相反规则。已核对的冲突位置（2026-10-23 当前文件）：

- `docs/FRONTEND_DESIGN.md:9`：「目录页入口仍按显式创建处理」→ 所有普通新建入口复用唯一槽位。
- `docs/FRONTEND_DESIGN.md:13`：「列出本标签页在该目录下未发送的新会话」→ 至多一个，并按槽位归属说明。
- `docs/FRONTEND_DESIGN.md:343`：「主动离开（返回目录）或更换 Agent/目录时清空草稿；更换 Agent/目录先 release」→ 普通导航保留；只有换 Agent 或显式放弃才清理，换目录不再原位替换。
- `docs/FRONTEND_DESIGN.md:348`：「显式放弃或更换 Agent/目录仍释放旧准备」→ 去掉目录替换。
- `docs/FRONTEND_DESIGN.md` §7 标签页生命周期条目：「主动导航、换 Agent 或目录先写逻辑删除墓碑」→ 只保留换 Agent/显式放弃/身份失效。
- `docs/SECURITY_DESIGN.md` §11.4 准备草稿条目中的同一「主动离开/换目录即清理」表述 → 与上条同步。
- `docs/INITIAL_DESIGN.md:133` Q18「草稿仅在内存、24 小时清理」→ 补充准备草稿窄例外。
- `docs/INITIAL_DESIGN.md` §3.7 若仍写「主动离页删除」→ 与 FRONTEND §4.6 统一。

PV1 的 `check:docs` 只校验链接，不能发现语义矛盾；WP1 的 reviewer 必须按上述位置逐条核对替换结果。

## Risks / Trade-offs

- 全量内容写事务增加存储成本 → 使用已有附件引用与内容编码，不复制附件字节；验证磁盘满及回滚，不削弱完整性。
- 回显缺少可靠上下文 → 保留独立事件优于误吞；以协议 fixture 验证首条、后续与旧端。
- 单槽位替换与恢复竞态 → 槽位代数、请求关联及草稿墓碑共同挡住迟到响应；不依赖组件卸载顺序。
- 性能采样可能含正文/凭据 → 只记阶段时间与本次测试标识，不记完整 prompt、证明、密钥。
- 前置变更验收未完 → 本变更独立记录所需基线和实测，不能声称替前置变更完成全部验收。

## Migration Plan

WP1 冻结值对象、端口、事务和 DDL 后，WP2 提供下一连续版本的 SQLite migration（现有 v16 准备表为基线，执行前核对实际版本），测试旧库升级及再次打开。只为新受理请求建立关联；不从历史回显推算旧输入。先实现 Owner 写入与回显，再更新前端替换逻辑，Daemon 与前端配套发布。

若无需新 wire 字段，维持 v1 既有字段；若 WP1 确认必须新增，登记 feature/schema/fixture 与旧端显式降级，未协商端不能宣称可靠本地合并。旧前端可能重复显示新 Owner 用户事件，发布时提示刷新并在兼容测试中覆盖，不删服务端正文来适配旧界面。

回滚前备份数据库；不向下删除用户输入或猜测兼容旧 DDL，旧二进制无法识别新 schema 时拒绝启动并恢复成套备份。准备槽位存储若改变记录版本，提供旧单定位迁移，未知版本显式不可恢复；不影响设备密钥和其他标签页。
