## Purpose

定义远端提交、节点共享排队并串行派发本地 Harness 的行为，区分受理、发送、插入和执行结果，使多客户端操作一致，并明确中断、失败暂停、重启及未知结果的边界。

## ADDED Requirements

### Requirement: 输入受理与防重复
系统 SHALL 在节点受理新输入时校验提交者身份、会话操作权限、目标及内容，登记稳定请求身份。同身份同内容返回原事实，不重复入队或派发；同身份不同内容 MUST 拒绝。主动追加相同文字可使用新身份；已安全清理的旧登记身份不得因记录缺失恢复资格。

#### Scenario: 断线后重复提交
- **WHEN** A 未收到受理响应，重连后用原身份和内容重试
- **THEN** 返回原队列项或处理结果，不增加输入或重复发送

#### Scenario: 请求身份冲突
- **WHEN** 原请求身份携带不同目标或内容
- **THEN** 拒绝冲突；编辑作为针对原队列项的独立操作受理

#### Scenario: 已清理身份再次提交
- **WHEN** 一个已安全清理的旧登记身份再次出现
- **THEN** 拒绝旧身份，新操作须取得新的登记身份

### Requirement: 受理授权由节点接管
系统 SHALL 在受理时固定输入目标、内容及授权事实；之后由节点负责，不要求原提交者在线，不因其后续权限变化自动取消，也不在派发时重新验证原提交者权限。新编辑、取消、立即发送及继续操作在提交时校验操作者当前权限；读取始终按读取者当前权限判断。

#### Scenario: 提交者断线或被撤销
- **WHEN** A 的输入已受理，随后 A 断线或被撤销
- **THEN** 输入保留并按节点规则执行；A 的新操作和读取被拒绝，停止旧输入须显式取消或中断

### Requirement: 每会话共享三个待发送输入
系统 SHALL 统一维护每会话最多三个未发送输入，所有客户端共享，挂起的旧项仍计入名额。入队和容量按节点顺序协调。失败挂起后新输入可在前台可用时直接派发，不占等待名额；不能立即派发则遵守共享三项上限，不建立第四个等待项。排队、发送、插入及执行结果分别展示。

#### Scenario: 最后一个队列名额并发提交
- **WHEN** 已有两个待发送输入，A、B 同时提交
- **THEN** 至多一个取得最后名额，另一明确队列已满，不覆盖已有内容

#### Scenario: 原生前台忙碌仍可排队
- **WHEN** 原生前台 active 或已有待插入输入，队列未满
- **THEN** 受理展示队列项，不立即向 Harness 派发

### Requirement: 多客户端共享查看和操作
系统 SHALL 向有读取权限的客户端展示同一节点队列及变化；有会话操作权限的客户端可编辑、取消或立即发送其他客户端提交的项。浏览器刷新、断线或换设备不清空节点已接收队列，各操作按节点事实同步，不由客户端建立独立派发队列。

#### Scenario: B 操作 A 的输入
- **WHEN** A 已排队三条输入，有相应权限的 B 打开会话并编辑或取消一条
- **THEN** B 可见和可操作同一队列项，A 和其他有权客户端看到相同结果

### Requirement: 队列无期限且不跨节点重启保存
系统 SHALL 不对已受理队列设等待期限，不因原提交凭证过期清理队列；未发送正文仅在当前节点运行期保存，不落盘、不跨节点重启恢复，也不要求专门的队列丢失提示。必要去重及已发生派发事实与正文分开保存，重启不得引起可能已发送动作重发。

#### Scenario: 长时间等待
- **WHEN** 队列等待超过一天
- **THEN** 不因时间经过失效，仍可查看、编辑、取消和在条件满足后派发

#### Scenario: 节点重启
- **WHEN** 节点带有未发送队列重新启动
- **THEN** 队列为空，不恢复正文、不增加专门丢失提示，不因缺正文重发旧动作

### Requirement: 排队输入可编辑
系统 SHALL 允许有会话操作权限的客户端编辑未发送输入，保留队列身份和位置，不新增名额；编辑作为独立操作记录实际操作者和新内容。编辑与发送按节点顺序处理，已开始发送的内容不可通过队列编辑改写。

#### Scenario: 编辑与发送交错
- **WHEN** B 编辑 X 与节点发送 X 相邻发生
- **THEN** 编辑先处理则发送更新内容；发送先处理则编辑失败并提示已发送

### Requirement: 队列取消与发送串行
系统 SHALL 按节点顺序处理取消和发送：取消先处理则移除该项，发送时项已不存在则不发送；发送先处理则队列取消失败并提示输入已发送。MUST 不将取消失败自动转为中断，也不同时报告同一项取消成功和发送。

#### Scenario: 取消先于发送
- **WHEN** 节点先处理取消 X，随后尝试发送 X
- **THEN** 取消成功，X 不在队列且不会发送

#### Scenario: 发送后取消
- **WHEN** X 已开始发送后客户端取消队列项
- **THEN** 提示取消失败、输入已发送；需要停止执行时另行中断

### Requirement: 同会话前台执行互斥
系统 SHALL 在同会话存在未结束前台、原生 active/unknown 或待插入输入时阻止下一条派发，不同会话可并行。正常队列在可靠成功后顺序推进；失败挂起的旧项只经显式继续恢复，失败后新输入按独立优先路径处理，但不绕过前台互斥。暂时忙碌不把零发送项记为交付未知。

#### Scenario: 成功后顺序派发
- **WHEN** 正常队列为 X、Y、Z，当前工作可靠成功结束且资源有效
- **THEN** 只发 X；X 尚待插入或未收敛不发 Y；若旧队列处于失败挂起则不因新工作成功自动恢复

### Requirement: 原生工作活动独立于平台输入记录
系统 SHALL 分别判断平台 Run、原生前台和后台事实；Agent 自发前台工作阻止派发但不补造平台 Run。前台结束不证明后台停止，后台及有效审批分别按资源和审批规格处理。

#### Scenario: Agent 自行开始前台工作
- **WHEN** 没有平台 Run 但有效连接报告自发前台工作
- **THEN** 保留队列等待，继续处理有效审批和中断，不建立虚假输入

### Requirement: 中断与立即发送
系统 SHALL 允许中断当前前台，确认结束后才派发。正常立即发送只选择已有未发送项，其他相对顺序不变，满队列新草稿不得成为第四个等待项。失败挂起后的新输入按“执行失败暂停队列”优先处理；不能立即派发时仍受共享上限约束。中断失败或未知保留输入并提示。

#### Scenario: 优先发送队列项
- **WHEN** 正常队列 X、Y、Z，用户立即发送 Y
- **THEN** 旧前台确认结束后只优先发送 Y，其余仍为 X、Z，旧取消不影响新工作

#### Scenario: 满队列立即发送新草稿
- **WHEN** 正常队列三项已满，用户立即发送未入队新草稿
- **THEN** 拒绝新增第四等待项；失败挂起后前台已可用的新输入可直接执行，不将其额外排入满队列

### Requirement: 执行失败暂停队列
系统 SHALL 在前台可靠失败后挂起原队列，保留内容及相对顺序，不自动发送。用户后续新输入在满足前台互斥和资源条件时优先于挂起项执行；新输入成功不自动恢复旧队列。只有有权用户点击继续后，旧项才按原相对顺序重新加入可执行队列，不复制或重复受理，也不抢占正在执行的新输入。旧工作可能活动时不得绕过异常重新准入。

#### Scenario: 失败后等待用户
- **WHEN** 当前 Run 可靠失败，原队列仍有 X、Y
- **THEN** 挂起并保留 X、Y；未点击继续不自动派发原项，但不阻止满足条件的后续新输入

#### Scenario: 失败后新输入插队
- **WHEN** X、Y 已失败挂起且前台可用，用户提交新输入 D
- **THEN** 优先执行 D；D 成功后 X、Y 仍挂起，不自动发送原项

#### Scenario: 显式继续后旧项重新排队
- **WHEN** D 执行期间或结束后，有权用户点击继续恢复挂起 X、Y
- **THEN** 原项恢复可执行状态并保持 X 在 Y 前，不重复入队、不抢占 D；轮到时再按串行规则发送

### Requirement: 取消与异常结果
系统 SHALL 区分未发送、可能发送、已插入及前台结果；同身份重试返回原事实。确定未发送的输入可继续派发，无法可靠核验的可能已接收副作用不得自动重发。执行慢或等待插入不是重发依据；异常保留真实未知范围。

#### Scenario: 派发后异常退出
- **WHEN** 输入可能被接收但响应丢失或节点退出
- **THEN** 查询核验可得事实，不能证明时保留未知，不自动重发或换身份重试

### Requirement: 插入确认与前台终态分别关联
系统 SHALL 分别保存请求插入、会话前台活动及 Run 结果，按各版实际依据关联。v2 终态先于插入响应时不清待确认输入，也不要求对端重发终态。内部顺序标记不是协议关联证明；证据不足时保留不确定性及核验、中断或资源收敛出口。

#### Scenario: 终态早到且交错自发工作
- **WHEN** 依次收到 active、idle、prompt 成功响应，并混有无法可靠区分的自发活动
- **THEN** 分别记录事实，不提前放行、不按最近 Run 猜归属，也不永久等待第二次 idle

### Requirement: 空闲取消与活动前台取消分开
系统 SHALL 在可靠 idle 且无待插入输入时不因中断新增等待额外 idle 的阻挡；活动、待插入及未知事实按实际协议处理。自然完成与中断交错时接受已证终态，不等第二个 cancelled；权限按该版实际取消范围回应。

#### Scenario: 取消与自然完成交错
- **WHEN** 中断前后已收到旧工作可靠正常终态，对端不再发 cancelled
- **THEN** 记录实际完成和中断未证实，不等第二个终态，不让旧取消作用于后续输入

### Requirement: 管理存储故障时限制危险派发并保持安全控制
系统 SHALL 区分去重、唯一派发、审批决定及资源归属所需事实和附加审计。必要事实无法可靠维护时停止相关新动作；仅附加审计失败时告警并可继续，不伪报保存成功。已有原生结果与记录故障分别表达，保留可验证的中断、拒绝和安全关闭路径。

#### Scenario: 附加审计失败
- **WHEN** 必要受理和去重可靠但附加审计写失败
- **THEN** 告警并按队列执行，不全局阻断，也不绕过批准决定必须保存

### Requirement: 异常后重新准入
系统 SHALL 分开判断旧工作是否活动和副作用是否已知；可靠确认旧前台及资源收敛，核验原生身份、归属及所需恢复后才派发下一条。断线、超时、新握手或未知标记不足以放行，未知结果不改为成功。

#### Scenario: 断线后旧执行仍可能运行
- **WHEN** 新连接握手成功但旧工作可能活动
- **THEN** 保留队列并阻止派发，先核验或安全收敛，不强杀共享实例其他会话

### Requirement: 节点时间与控制并发
系统 SHALL 用节点时间记录管理事件，按节点处理顺序排队；客户端时间不影响受理和排序。输入受理和派发不依赖统一24小时期限、回退锁定或持久时间水位。审批和中断不得排在普通输入后等待，长时执行、插入、读取及用户选择不得堵住接收或控制。

#### Scenario: 校时及等待审批期间接收控制
- **WHEN** 节点校时、Run 等待审批，B 同时编辑队列并中断
- **THEN** 不因校时过期输入或锁定派发；有权控制独立处理，不等 Run 或普通队列结束

### Requirement: 命令记录不成为聊天历史
系统 SHALL 只持久保存必要管理和结果元数据，不以队列、命令、审批建立永久聊天档案；未发送正文及编辑旧版本不永久保存。正文和输出缓存限制遵循 acp-platform-constraints，不把旧平台预算冒充 ACP 要求。

#### Scenario: 查询排队与执行结果
- **WHEN** 客户端查看队列或已发生结果
- **THEN** 分别显示受理、发送、插入和实际结果，不补造成原生聊天历史

### Requirement: Windows 与 Web 操作闭环
系统 SHALL 提供 Windows 节点及 Web 会话输入、共享队列、结构结果、审批、中断和显式释放；资源未释放时一轮结束仍显示运行中，释放确认后才显示空闲。

#### Scenario: 一轮完成
- **WHEN** 回复完成但资源仍加载
- **THEN** 显示本轮结果和共享队列，同时资源仍显示运行中
