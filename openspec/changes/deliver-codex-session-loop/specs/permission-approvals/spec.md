## Purpose

定义 Harness 权限请求的可见内容、有效期限、唯一裁决与实际交付之间的区别，保证多个客户端无法重复批准同一请求，断线或恢复也不会复用已失效审批，同时保留协议选项和操作者可追溯性。

## ADDED Requirements

### Requirement: 保留审批语义
系统 SHALL 展示协议提供的请求内容、选项与作用范围；未知选项或不支持的审批能力 MUST 明确报错，不静默转换为自由文本或默认允许。

#### Scenario: 不支持的请求
- **WHEN** 收到无法正确表达的审批请求
- **THEN** 系统明确呈现限制，不代替用户批准

### Requirement: 审批事实独立于聊天缓存
系统 SHALL 从当前有效连接验证审批来源并展示实际请求，持久记录必要裁决及交付元数据，不依赖平台聊天正文保存或强制刷新；MUST 不因移除历史持久化削弱来源校验，也不永久复制完整提示词或工具正文为审批档案。

#### Scenario: 展示缓存失败时已有审批
- **WHEN** 已准入连接有可验证的有效审批请求，但展示缓存或本次历史重放暂时失败
- **THEN** 对仍有效的实际请求按唯一裁决及交付规则处理，不因展示失败默认允许或复活旧请求；此行为不授权无重放能力的接入绕过基础门禁

### Requirement: 唯一裁决与交付分离
系统 SHALL 对有效请求最多接受一个最终决定，分别记录裁决和交付结果；交付不明或失败 MUST 不被记作已送达，也不自动重复发送可能产生副作用的决定。

#### Scenario: 两客户端同时审批
- **WHEN** 两个客户端对同一有效请求提交不同决定
- **THEN** 至多一个决定被接受，另一方得到已裁决结果

#### Scenario: 决定交付失败
- **WHEN** 决定已接受但连接丢失导致交付无法确认
- **THEN** 保留原决定并显示交付未知，不宣称已获 Harness 执行

### Requirement: 决定持久化失败不授予权限
系统 SHALL 在批准决定及唯一裁决所需事实可靠提交后才向仍有效请求交付批准；提交失败或结果未知时 MUST 不发送允许结果、不报告决定已可靠接受。只有查明既有决定、请求有效性及交付事实后才可按原事实处理，不能因用户重试重新裁决或重复交付。对无法安全批准的有效待处理请求，可以按当前协议安全拒绝或取消等待，并明确报告管理记录失败；协议安全响应不是新的用户批准，也不覆盖已保存的用户决定。已发送决定后交付结果写入失败时保留发送及不确定事实，不重新发送，存储恢复后重新核验。

#### Scenario: 批准保存失败或提交未知
- **WHEN** 用户选择允许，但决定事务失败或无法确认是否已提交
- **THEN** 不向 Harness 发送允许结果，不接受另一个互相冲突的决定；按协议安全拒绝或取消等待并说明记录失败，不让等待记录恢复成为默认允许

#### Scenario: 已有允许决定随后协议要求取消
- **WHEN** 允许决定已保存但尚未交付，原生请求随后失效或协议要求回应 cancelled
- **THEN** 不再交付允许；按协议完成安全响应，保留原用户决定及实际交付结果，不将安全响应误记为第二个人工最终裁决

#### Scenario: 已发决定但交付记录失败
- **WHEN** 允许或拒绝响应可能已发送，但交付结果无法提交管理存储
- **THEN** 说明交付记录失败及可证明范围，不重复发送响应、不复活请求；原生实际执行结果不因管理记录失败被改写

### Requirement: 审批关联真实原生操作上下文
系统 SHALL 将审批绑定到节点验证的原生目标、实例、有效 Harness 连接代际及当前真实请求，并按协议实际提供的依据关联原生操作上下文；该上下文可以是加载、恢复、输入引发的工作，也可以是会话内的后台或 Agent 自发工作。只有可靠证明属于平台输入时才关联 Run，关联用于追溯而不替代请求有效性判断。MUST 不为审批伪造聊天轮次或 Run，不用客户端自报上下文代替节点验证；协议只提供会话及当前请求归属时，不额外要求其证明精确前后台类别或平台 Run。无法验证目标、连接或真实请求时保持未授权并明确失败。

#### Scenario: 加载审批无输入执行
- **WHEN** 当前加载操作产生可验证权限请求，但没有平台输入 Run
- **THEN** 展示真实操作及请求范围，允许按有效选项裁决，不新建虚假输入或执行轮次

#### Scenario: 上下文失效后交付
- **WHEN** 裁决已受理，但交付前有可靠事实证明请求已失效、其专属原生工作结束并使请求失效，或连接代际改变
- **THEN** 保留原裁决事实，拒绝向失效操作或新连接交付，不从旧记录恢复授权

#### Scenario: 无法证明审批归属
- **WHEN** 请求无法验证为节点管理目标在有效连接上的当前真实权限请求
- **THEN** 明确报告关联失败，不默认允许，不借用其他 Run 或加载操作的权限

### Requirement: 请求有效性受原执行约束
系统 SHALL 按当前协议的请求、工作取消及会话生命周期判断审批有效性；请求被取消、已答复、连接代际失效，或有可靠依据证明其专属原生工作已经结束且请求失效时拒绝旧审批。平台 Run 完成、前台转为空闲或加载请求返回本身 MUST 不被当成所有会话审批失效的证据；仍有效的后台请求不随其最初关联的 Run 结束而失效。协议要求取消会话的全部待处理权限请求时，按该规则逐一回应，不因无法区分前后台而遗漏。恢复会话不让旧请求重新生效；新连接重新建立的真实请求须重新验证并独立裁决，不能复用旧决定。

#### Scenario: 恢复后批准旧请求
- **WHEN** 用户对异常前的待审批请求操作
- **THEN** 系统拒绝为过期请求，不向新连接发送该决定

#### Scenario: 前台结束后后台请求审批
- **WHEN** 平台输入对应的 Run 已结束，但同一有效连接上的原生会话仍有后台工作并发出真实权限请求
- **THEN** 校验会话、连接及请求后正常展示和处理，不因没有活动 Run 拒绝，不创建虚假 Run；该有效审批继续保护所属主执行树

#### Scenario: 前台结束时后台审批仍待处理
- **WHEN** 会话报告前台结束，但一个已验证的后台权限请求仍有效且尚未答复
- **THEN** 保留该请求及唯一裁决边界，不因 Run 终态或前台空闲批量失效；请求后来取消或连接失效时才按真实事实失效

#### Scenario: 协议不区分请求的前后台归属
- **WHEN** 当前协议仅提供可靠会话、连接及权限请求标识，没有可验证的前后台类别或平台 Run 关联
- **THEN** 以这些真实归属校验请求，不猜测借用最近的 Run，也不把缺少精确工作分类当作来源无效；取消时遵循该版协议规定的请求范围
