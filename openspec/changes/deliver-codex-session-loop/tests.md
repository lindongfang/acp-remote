本文件定义 deliver-codex-session-loop 的验收用例，不记录执行结果。依据本次测试流程修订，保留 CL-001–042 的稳定编号和标题，每例仅列用例级别、操作步骤和预期结果；需求关联与执行信息在下方集中说明。裸 specs 路径只指本 change 增量，不跨目录补位。

仓库已有上游节点和 Web 开发实现及构建入口，本 change 的会话闭环仍待实现；开工前核对上游固定版本、合同和实际能力。已有工程入口不等于本 change 已被测试，缺少工具、环境、权限、真实对端或专用测试入口记受阻/未执行，不自动转为 LX，不用模型推断代替执行证据。

## 修订与执行边界

保存参数依据重设计 §5.3：500 毫秒或 64KiB 先满足者提交，条目/执行结束、审批前和正常释放强制刷新；不沿用早期的 250 毫秒/256KiB。依据 2026-10-29 保存展示要求及本 change 规格/design，正常页面隐藏保存中、未保存、已保存和提交版本，仅保存失败、异常丢尾或完整性无法确认时显示错误；内部版本、缓存限额与失败停止规则保持。

ACP v1/v2 是兼容目标，须核实官方规范地址、修订、实际标识及稳定/草案状态；JSON-RPC 2.0 或 SDK 号不是 ACP v2。仅测实际可用的 Harness × 协议版本 × 能力组合；缺规范、实现或真实对端记受阻/未执行，不声明 v2 已验证，也不静默只交 v1。CL-033 保留重设计 §4.5 与 R-ACP-003 修订依据，区分取消前有效审批、取消后的请求处理和本轮可靠完成。

## Cases

### CL-001 真实构建及类型检查

- 用例级别：L1
- 操作步骤：在仓库根目录按 README 和 package.json 执行 npm run check、npm run build:rust；另执行 openspec.cmd validate deliver-codex-session-loop --strict 与 git diff --check，分开记录规划检查和产品构建结果。核对构建目标是否实际包含本 change 的节点与 Web 实现。
- 预期结果：真实编译、Web 构建与类型检查成功，检查覆盖本 change 的实际目标；现有上游开发实现通过构建不证明会话闭环通过。缺本 change 的目标或检查入口记受阻/未执行，规划校验不能代替编译或功能验收。

### CL-002 静态合同和供应链检查

- 用例级别：L2
- 操作步骤：在仓库根目录执行 npm run check、openspec.cmd validate deliver-codex-session-loop --strict、git diff --check、npm audit --audit-level=high；对真实 BASE/HEAD 执行 npm run lint:commits -- --from BASE --to HEAD --verbose，按 .github/workflows/ci.yml 的 secrets 作业执行密钥扫描。核对本 change 的协议合同、依赖审查和锁文件是否纳入适用入口，未建立的专用合同入口记未执行。
- 预期结果：真实适用检查按工程配置执行；开发工具审计不等于产品供应链通过，无专用结构门禁，reviewer人工核对精确引用和覆盖。

### CL-003 领域边界及异常状态

- 用例级别：L3
- 操作步骤：以可控时钟、计量缓存和协议fixture分别构造：空闲会话双客户端输入、同请求异内容、取消已发送但prompt未结束、旧连接审批、工具更新及未知字段。保存分支每次从干净状态开始，记录首个脏数据时刻，在未满64KiB时检查499ms/500ms，另在未满500ms时累计到64KiB前一字节/恰好64KiB；分别触发条目结束、执行结束、审批前及正常释放，检查无需等待周期的刷新请求。会话/节点限额按design默认16MiB/128MiB，使用不完成写入的存储替身分别隔离时长、大小、高水位与硬上限条件；以ceil(0.8×限额)前一字节/恰好高水位、硬上限前一字节/恰好硬上限及继续输入检查受理、刷新、取消、缓存占用及缺失范围；持续失败分支使用实施时明确登记的失败判据，未定义则记受阻，不自行编造重试次数。最后交错当前版本5、提交版本3与成功提交确认，检查内部版本及页面视图映射。
- 预期结果：干净且可执行的同会话并发输入只受理一个，另一返回忙碌；同请求异内容拒绝且零新增派发，取消未可靠完成前普通输入仍拒绝，旧代际审批不交付新连接。工具更新保留原条目ID/首次位置，未知字段保真且无跨条目合并。无结束/审批等强制条件时，499ms且未满64KiB不因周期提交，500ms或64KiB先到者请求提交；强制刷新不等待阈值。高水位前不因容量门槛拒绝，达到任一高水位停止受理新输入并立即刷新；持续失败满足登记判据或达到任一硬上限时请求取消并协调停止所属输出，缓存不越过限额无限增长，溢出和未提交范围明确。当前5/提交3独立保留，旧版本不盖新，正常提交不生成页面保存状态；失败与完整性无法确认仍产生错误。局部替身结果不代替真实平台或Harness证据。

### CL-004 事务资源与并发协作

- 用例级别：L4
- 操作步骤：在隔离真实SQLite中为受理事务的Command、用户输入、Run写入及提交设置可控故障点，分别在事务提交前、提交后派发前、派发后终态前终止本次节点并重启，记录三类记录、原请求查询结果和协议对端派发计数。两客户端通过屏障同时提交相反审批决定，再在唯一裁决提交后、交付确认前断开所属连接，重试决定并尝试旧代际审批。对同一工具条目依次发送开始、后续文字、工具完成，比较数据库ID、首次位置和版本；交错保存旧版本与新版本并在提交中断后重启。最后在释放强制刷新及底层关闭分别注入失败，检查操作结果、实例/任务所有权及审计；每个分支恢复干净测试副本后单独运行，注明真实或模拟对端边界。
- 预期结果：受理事务提交前失败不留下部分Command/用户输入/Run且零派发；提交后派发前崩溃保留原受理关联并标记中断/未知，不自动补发；派发后无可靠终态重启不增加派发次数，同请求查询返回原关联。有效并发审批恰有一个裁决被接受，另一返回已裁决；交付无法确认保留原决定与未知事实，重试和旧代际决定不产生第二次交付或新授权。工具完成只更新原ID，后续文字位置不变，内容/提交版本不回退且未提交内容不冒充持久化。刷新或关闭失败不返回正常释放成功、不凭断线显示空闲，相关资源或未确认事实仍由节点追踪，审计区分受理、裁决、交付和释放结果；关闭与取消后本次任务/进程树有可核对的所有者和清理结果。

### CL-033 逐版本完成取消与互斥合同

- 用例级别：L4
- 操作步骤：分别按已核实 v1/v2 规范构造正常完成、取消已发未完成、可靠完成、错误版本信号及异常断线；各阶段提交普通输入。取消前对仍有效审批提交决定；另保留当前轮次待处理权限请求，取消后检查各版本规定的处理及随后旧审批决定。依据重设计 §4.5，v1 检查相关 session/request_permission 回复 cancelled，以及原 session/prompt 最终响应与结束原因；其他版本仅使用其核实规范，不套用 v1 信号。
- 预期结果：取消前仍有效审批可接受唯一裁决；取消后按所属版本规范处理相关待处理权限请求，v1 必须回复 cancelled 并拒绝后续旧审批决定，不向 Harness 发送旧授权。仅所属版本可靠完成事实才结束本轮并解除前台互斥；发送取消、权限取消响应及错误版本信号均不等于本轮完成，未完成期间普通输入仍被拒绝。本轮完成不等于资源释放，异常不重发。修订依据为重设计 §4.5 对执行、取消及权限请求的逐版本约束，修复 R-ACP-003 的取消前后混淆。
