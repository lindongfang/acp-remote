## 共用执行安排

- 本独立tester只维护验收定义，全部产品用例未执行。主执行获Q-002窄授权删除ACP累计请求阈值并另行回归；本候选不代签该代码验证，也不扩展为完整队列实现授权。候选结构检查只核对定义，不代表需求已经实现。正式实施前，由独立 reviewer 核对场景覆盖和新增迁移、队列交接、原始帧关联及有效配置合同；已核对本轮 plan 的 WP1→WP5候选→WP6 顺序及后续 WP2→WP3→WP4 依赖；正式执行仍须冻结具体执行者、独占数据/端口/target和可用入口，不把工作包角色安排当实际资源已备齐。
- 裸 `specs/<capability>/spec.md` 仅指本 change 增量；长期规格显式写 `openspec/specs/...`。Q-001 取代旧 RP-001/R2 冲突规则，Q-002再取代“失败后所有新输入也须等继续”的解释；旧实现、已勾任务、旧合同与历史测试不作为新规则通过证据。详细合同只在与当前 specs/design 一致且已独立检视的范围使用。
- L1/L2 入口来自 README、根与 clients/web 的 package.json、.github/workflows/ci.yml；只读取了实际配置，未运行检查。L3 为纯模型/协议夹具，L4 为自有真实 SQLite 事务及可控协议/故障替身；L5 经实际节点认证入口与真实存储/传输，Harness 可为明确标记的合同对端；L6 的节点、Web、SQLite、Harness/适配器、原生来源及 Windows Job 进程树均须真实。协议替身、传输故障窗口和模拟时钟必须标清边界。
- 现有 `cargo test --manifest-path app/Cargo.toml --test session_loop_acceptance --locked` 及 `acp_message_id_acceptance`、`acp_view_observations_acceptance`、`acp_tool_projection_acceptance`、`domain_borrow_acceptance` 等仅作为可用入口定位；其内部现有期限/预算等旧断言须先按本文件重基准。L3 先行不完成 L5 义务，CL-086/100/101 的节点合同验证不替代 CL-030/046/054/057/060/085/105–107/114 的真实分支。
- 缺新入口、故障点、权限、环境或真实能力记受阻/未执行，不转 LX，不用零测试、仅启动、截图或自测代签。本轮没有必须由人员判断而工具不能验证的内容，不设 LX。能力未提供的可选真实分支单独记录，不能据此给整个必需链路通过。
- 正式执行固定同一提交或 SHA-256 清单、官方协议修订、受测程序/适配器/配置与迁移版本；tester/reviewer 使用独立数据根、原生来源、端口、可信客户端和进程。页面交互优先 ego-browser，稳定回归用仓库实际入口。失败和取消仍清理自有资源，保护用户数据库、凭据、被忽略文件及原生会话，输出脱敏。
- 测试结果另存 `testing/runs/deliver-codex-session-loop/`，逐 ID/分支记录版本、环境、实际数量、命令、实际/预期、证据及清理；必要失败/未执行不判通过。安全/供应链/真实 Harness/独立检视分别保存。相同版本与范围证据可复用，影响变更后独立判断失效，不改写历史结论。
- 自动回收、完整历史任意定位/子树、原生删除和管理元数据清理各归所属 change；本期只验相应能力呈现、安全保护及已交付接口，不把端口夹具当下游实现。附件实际读取的独立安全预算、既有认证通道和资源数量规则仍按负责规格，不与已删除正文/输出预算混淆。

## 长期规格复用及回归范围

- `openspec/specs/node-access/spec.md` 及 `testing/suites/node-access/tests.md` 仍负责节点身份、网络认证、本机 OS 身份、进程所有权及重启信任；本 change 不把删除每动作签名/输入期限扩展为取消既有控制通道认证。
- `openspec/specs/client-trust/spec.md` 及 `testing/suites/client-trust/tests.md` 仍负责认证、当前读取/新操作撤销、信任与实时审批分离。其长期归档设备撤销期限不被本轮输入无 TTL 覆盖；已受理工作由节点接管的交界由 CL-092/093 验证。

## Cases

### CL-001 真实构建及类型检查

- 用例级别：L1
- 操作步骤：按 README、根 package.json 与 clients/web/package.json 执行 npm run check、npm run build:rust；Windows 测试按 testing/ci/windows-owner.ps1 准备实际 owner 环境。另执行 openspec.cmd validate deliver-codex-session-loop --strict、git diff --check。记录各入口实际测试数量、退出码和快照。
- 预期结果：编译、Web 类型/测试/构建、Rust 格式/clippy/测试及文档检查分别有结果；零测试、仅静态通过或旧合同测试通过不视为 Q-001 功能通过。

### CL-002 静态合同和供应链检查

- 用例级别：L2
- 操作步骤：按 .github/workflows/ci.yml 执行依赖审计与密钥扫描，检查产品依赖审查/锁文件，真实 BASE/HEAD 用 npm run lint:commits -- --from BASE --to HEAD --verbose；逐项核对本文件场景引用与实施合同。
- 预期结果：供应链、提交和静态合同检查分别可追溯；上游或开发工具审计不代替产品依赖审查，无专用脚本时人工核对而非虚报机器验证。

### CL-003 领域边界及异常状态

- 用例级别：L3
- 操作步骤：确定性模型覆盖节点登记去重、共享三个等待项、入队/编辑/取消/发送先后、正常优先中断、失败挂起旧项与新输入优先、点击继续恢复、受理后撤销、独立原生活动及早到终态；另执行CL-043–045/056/066/067/072–074/100和110–113的模型分支。
- 预期结果：数量、队列身份、可执行/失败挂起状态、前台与插入事实独立；并发结果对应节点顺序，新输入成功不恢复挂起旧项，继续不重复受理或抢占当前工作；模型只证明其输入前提下规则。

### CL-004 事务资源与并发协作

- 用例级别：L4
- 操作步骤：用自有全新库及 schema1/2/3/4 一致性副本，对编码前独立检视通过的新迁移合同逐事务注入失败并核对原身份、信任、撤销、管理及旧正文摘要；在必要登记、审批保存和派发交接前后崩溃。并发相反裁决与连接失效交错，检查正文/编辑旧版本未落盘。
- 预期结果：迁移原子且失败回滚，未知/残缺库拒绝不重建；旧数据保留，新入口不读写旧正文；必要事实可靠后方可派发，队列正文不恢复，可能发送不补发，裁决唯一。当前尚未冻结的新 DDL 不预设 schema5 或宣布可执行，缺合同/入口记录受阻。

### CL-005 能力未证实

- 用例级别：L5
- 操作步骤：登记 Harness 与目录；当前身份权限、请求去重、真实原生请求及资源安全条件满足时，分别给出仅缺程序实测报告但标准能力可用、Harness 明确声明不支持、标准调用返回不支持错误，以及平台尚未实现协议版本或操作的组合；查看实际 ACP 声明、调用与错误归属。另保安全条件不满足的拒绝对照。
- 预期结果：仅缺该程序实测报告不阻止已实现标准路径，证据仍标未实测；Harness 不支持直接呈现 ACP 声明或实际错误，平台未实现则明确报平台尚不支持并保留对端声明，不混称 Harness 不支持。不另建平台能力准入矩阵、兼容验证或等待用户决定流程，不私有兜底、不创建替代会话、不伪报成功；权限、去重、真实请求及资源安全仍独立执行，不冒额外 ACP 能力证明。登记不自动运行有副作用探针，不泄露配置凭据。

### CL-006 页面断开

- 用例级别：L5
- 操作步骤：真实节点执行中关闭/断网/退订页面，再用另一可信客户端查看已保留输出和有效审批；观察节点所有者及调用。
- 预期结果：客户端断开不取消工作或 Harness 连接，节点继续管理；退订只影响该订阅，不清空共享视图，不承诺已交网络栈数据收回。

### CL-007 共享实例释放

- 用例级别：L5
- 操作步骤：同实例两个自有会话并行，对一个显式释放；在可隔离及不可隔离两分支核对另一会话与资源树。
- 预期结果：可隔离则只释放目标，不能隔离则明确拒绝并保留责任；不强杀其他会话，不凭缓存清空判释放。

### CL-008 释放失败审计

- 用例级别：L5
- 操作步骤：令释放已受理而关闭失败/超时，查命令、审计与另一客户端状态；对照真实关闭确认但管理结果未保存。
- 预期结果：受理/关闭/结果持久化分别表达，失败或未知不记完全成功，不显示空闲或复用未协调容量。

### CL-009 已撤销客户端访问

- 用例级别：L5
- 操作步骤：两个可信客户端订阅/读取会话、队列、引用块、附件及审计，屏障撤销其一；撤销COMMIT后尝试新输入/取消/编辑/继续、订阅及逐块读取，另观察其撤销前已受理输入。
- 预期结果：撤销后新受理及尚未交网络栈的受保护读取停止，缓存/引用不绕过身份；撤销前已受理输入继续由节点规则处理，不因撤销自动取消，不声称收回已写字节；错误无敏感正文或凭据。

### CL-010 原生状态缺失

- 用例级别：L5
- 操作步骤：先有缓存及管理绑定，再让原生会话无法读取/恢复；清缓存后查看与继续输入，检查原生调用及绑定。
- 预期结果：明确原生缺失或读取失败，管理审计仍可查；不拼接命令/审计为聊天、不承诺旧全文、不静默新建或灌入平台副本。

### CL-011 释放时保存失败

- 用例级别：L5
- 操作步骤：在隔离真实节点对显式释放注入管理记录写失败及底层关闭失败，确保操作者与资源仍可验证；共享实例保留另一会话。解除故障后核验并补记，再观察容量。
- 预期结果：不再有聊天强刷前提；仍尝试安全收敛，实际关闭与记录失败分别报告，未持久协调不报完全成功/空闲或复用容量；共享会话不受强杀。

### CL-012 恢复重放旧消息

- 用例级别：L5
- 操作步骤：恢复时重放旧条目及重复正文的不同条目，分别有可靠来源关联和无跨加载 ID；混入实时输出及旧代际迟到响应。
- 预期结果：旧历史不成新回复；可靠关联才衔接，无依据重建/分开并说明限制，不按文字/摘要去重，不让旧代际覆盖新视图。

### CL-013 不支持的请求

- 用例级别：L5
- 操作步骤：协议对端给未知主题、未知选项提示种类但真实请求及 optionId 可验证的请求；人工选择原广告选项。对照结构错误、伪造选项、已取消请求，以及无 Run/精确前后台类别但归属真实的请求。
- 预期结果：未知展示扩展安全通用展示并说明限制，用户可选择真实原选项；未知内容不自动允许。错误结构/伪造选项/失效请求拒绝，缺 Run/工作细分类本身不构成来源无效。

### CL-014 两客户端同时审批

- 用例级别：L5
- 操作步骤：两个可信客户端屏障同时提交相反决定，再以原身份重试；统计决定记录与实际 writer 响应。
- 预期结果：最多一个最终用户决定，另一方得到原裁决事实；同身份不二次交付，不把传输写入当原生执行成功。

### CL-015 决定交付失败

- 用例级别：L5
- 操作步骤：唯一裁决保存后在交付前、可能写入后分别断连接或写失败；重试原决定并查询交付事实。
- 预期结果：保留唯一决定，未交付/未知/可证发送分开；未知不自动重发，不向新连接复用旧授权。

### CL-016 恢复后批准旧请求

- 用例级别：L5
- 操作步骤：异常后恢复同原生目标，操作旧连接待审批记录；再令新连接产生同标量 ID 的新真实请求。
- 预期结果：旧请求失效且零旧决定交付；新请求重新校验并独立裁决，不复用旧允许。

### CL-017 断线后重复提交

- 用例级别：L5
- 操作步骤：节点已登记输入，在响应丢失、浏览器重连及等待超过一天后用同 ID 同内容重试；分别让其仍排队、已发送、已完成及节点重启失去未发正文。查询节点事实及实际派发次数。
- 预期结果：重复返回原事实，不重复入队/派发；无统一期限。重启旧项不靠重试恢复正文，元数据仍防重；主动追加同文字须新登记身份，未发送与可能发送分别处理。

### CL-018 请求身份冲突

- 用例级别：L5
- 操作步骤：使用已登记 ID 改目标、动作或内容提交；同内容合法表达对照。另以有权 B 的新操作编辑原等待项并重试编辑操作，再用原提交 ID 携带编辑内容。
- 预期结果：登记 ID 内容冲突拒绝，原队列不被偷换；合法重复只返回原事实。编辑是新验权操作，保留项身份/位置并记录内容版本和实际操作者；不要求独立每动作签名、截止或时间水位。

### CL-019 并发输入

- 用例级别：L5
- 操作步骤：同来源同原生 ID 当前前台活动时，A/B 跨入口同时提交四条普通输入，再释放当前工作；对照不同会话共享目录并行，期间处理审批和中断。
- 预期结果：最多三个等待项全客户端共享，满额明确拒绝且不覆盖；前台至多一个，可靠成功后 FIFO 逐条派发。忙碌可入队但不派发，目录不建立锁，控制不排在普通输入后。

### CL-020 取消未完成

- 用例级别：L5
- 操作步骤：活动前台或已发送待插入输入存在时中断，只给取消发送/适用权限响应而无可靠终态；再提交普通输入，并对照空闲无 pending 分支。
- 预期结果：不把中断发送当已结束，不解除旧工作派发阻挡；剩余名额可排队，不向 Harness 发下一条。满额拒绝；空闲无 pending 按 CL-072 不新增额外等待。

### CL-021 派发后异常退出

- 用例级别：L5
- 操作步骤：输入可能已接收并产生副作用后断线/节点退出，无可靠终态，重启并重试旧登记ID；重新登记新输入并在需要时取得原生恢复，观察入队/派发及资源责任。
- 预期结果：已知发送与未知结果分开，不补发可能发送项，旧登记不因重启复活；所需恢复按当前能力校验，名额内可受理项与旧活动阻派发分别呈现，未知不改未发生，不从管理事实拼原生消息。

### CL-022 一轮完成

- 用例级别：L5
- 操作步骤：真实完成一轮但保留资源，再确认显式释放；另让关闭未确认，比较 Web 的前台结果与资源状态。
- 预期结果：一轮完成单独显示，资源仍加载时页面运行中；仅释放及管理协调确认才空闲，断线/idle 不替代释放。

### CL-023 工具晚完成

- 用例级别：L5
- 操作步骤：在实际版本与可证明的同一来源/身份内，依原生顺序提供工具 T 开始、后续文字 A/B、T 的进度更新、文字 C、T 的再次更新及最终状态/结果；逐次比较 T 首次位置和身份、A/B/C 的正文及相对顺序、条目数量，再重放重读。另给来源不足以证明同一工具的对照。
- 预期结果：每次进度、状态及最终结果都更新首次出现位置的同一 T；A/B/C 正文与原相对顺序保持，不把 T 移到完成处或列表末尾、不按类型重排、不追加同一工具的重复完成条目。有可靠来源关联才更新或避免重读重复；来源不足时明确限制、不猜测合并，也不复制为新回复。

### CL-024 未知结构载荷

- 用例级别：L5
- 操作步骤：实时及重放提供未知结构/扩展、必要原始字段和支持结构；内容超过旧单对象/实体预算，读取安全视图与惰性原始数据。
- 预期结果：保留实际结构、来源和字段，未知明确显示限制，不静默降文本或执行主动内容，不因旧内容预算截断；真实分配/协议失败如实报告。

### CL-025 保存失败

- 用例级别：L5
- 操作步骤：使展示缓存更新/分配失败，同时管理存储及 Harness 连接健康、真实审批有效；观察工作、审批和错误。
- 预期结果：缓存故障报告读取限制且不当原生保存失败，不仅因此取消工作；有效审批不依赖聊天强刷仍按唯一裁决处理。

### CL-026 持续保存故障

- 用例级别：L5
- 操作步骤：持续流式输出跨越旧视图、实体、节点缓存与快照阈值；慢订阅暂停消费，随后恢复并核对已接收输出。并行审批、中断和队列操作，另注入真实展示故障及必要管理存储故障。
- 预期结果：不以旧输出容量驱逐、截断或间接正文限额，慢客户端不堵协议接收及控制；实际展示故障准确报告且不取消原生执行。必要管理故障按 CL-075–078，附加审计故障按 CL-094。

### CL-027 实时尾部丢失

- 用例级别：L5
- 操作步骤：已有原生历史与实时尾部时重启节点，确认内存视图丢失；让原生分别返回完整、压缩后历史及读取失败。
- 预期结果：从 Harness 重建实际可读内容，原生不再保留的尾部不补造；错误明确，不从平台管理记录恢复聊天，不宣称显示即已保存。

### CL-028 目录失效

- 用例级别：L5
- 操作步骤：登记可用目录后删除/改为文件/撤销访问，再请求执行；对照有效绝对路径与含转义路径。
- 预期结果：节点解析真实路径，失效明确拒绝且不启动工作，不静默切默认目录；路径访问检查不冒充文件修改隔离。

### CL-029 两个会话共享目录

- 用例级别：L5
- 操作步骤：两个不同原生会话同时选择相同有效目录并执行；对照同一原生目标跨入口。
- 预期结果：不同会话允许并行，不因目录相同拒绝且不承诺冲突解决；同目标仍共享前台互斥。

### CL-030 真实Windows与Web闭环

- 用例级别：L6
- 操作步骤：固定真实Codex/适配器、规范、摘要与实际ACP版本，在专用Windows数据/原生根和可信Web完成登记、创建、输入、结构工具、真实审批、中断、跨端查看、释放、同原生身份恢复及重启；加入共享队列、A撤销后旧受理交付、失败挂起后新输入优先/成功不恢复旧项/显式继续、编辑取消，逐分支核对自有树。
- 预期结果：节点/Web/SQLite/Harness/原生数据/Job全链路真实；无重复副作用，历史按真实重放或当前连接模式呈现并有提示，不设旧内容预算。失败挂起只约束旧项，新输入仍按互斥/资源条件派发。未产生的真实分支列未执行，不用握手、截图或替身补签。

### CL-031 独立安全及交互检视

- 用例级别：L5
- 操作步骤：独立 reviewer 对固定集成快照检视认证、读取撤销、受理授权与节点交付交接、来源、唯一裁决保存、请求有效性、共享资源关闭、输入内存生命周期及内容/资源安全；用浏览器/协议故障工具核实关键边界。
- 预期结果：独立问题与结论可追溯，自查不能代签；撤销后停止新操作与读取，但不撤回受理输入或已保存决定；无敏感内容泄漏或旧正文接线，未知不虚报成功。缺执行证据保持未验证。

### CL-032 相同标准合同不按厂商分流

- 用例级别：L5
- 操作步骤：两个不同名称的协议合同对端使用相同标准版本与能力，运行同组执行/审批/取消/重放；若有两款真实程序再分别记录。
- 预期结果：共用标准合同、不按厂商分流；合同对端不标真实跨款通过，真实范围单独记录，缺第二款不虚报。

### CL-033 逐版本完成取消与互斥合同

- 用例级别：L4
- 操作步骤：按已核实 v1/v2 规范分别构造完成、插入确认、取消发送/权限取消、自然完成及错版控制值，逐步尝试普通输入。另执行 CL-072–074 边界。
- 预期结果：v1 可靠 prompt 终态与 v2 插入/前台状态不混用；发送取消或重放快照不等于活动完成，取消按该版请求范围处理；idle 无 pending 不等协议未要求通知。

### CL-034 逐版本结构与未知载荷保真

- 用例级别：L3
- 操作步骤：逐版本输入结构更新、工具字段省略/null/patch、未知扩展和未知主题/选项提示；验证原 optionId 人工选择与伪造 optionId 拒绝，对照原始字段及安全投影。
- 预期结果：按实际版本保留语义，不通用深合并或跨版解释；未知结构惰性保留，未知审批可安全展示和人工选原选项但不自动允许；不以正文持久化验证保真。

### CL-035 无共同版本拒绝与零派发

- 用例级别：L4
- 操作步骤：对端仅提供无共同支持或未实现/无法核验版本，尝试产品创建、恢复和输入，统计调用。
- 预期结果：版本缺口明确且零业务派发，不猜格式/静默换版或创建替代会话。

### CL-036 协商回退不得重复副作用

- 用例级别：L4
- 操作步骤：核验合法高版 offer→低版 selected 的响应 ID/schema，另给未知/超 offer 选择、错响应 ID、错 selected 形状和网络/业务失败。
- 预期结果：仅规范允许的协商结果生效，按 selected 解析并绑定连接；错误不重新试发副作用，不按厂商猜版本，不将网络/认证/业务失败作为降版证据。

### CL-037 版本规范依据与平台未支持说明

- 用例级别：L5
- 操作步骤：核对实际协议版本标识及平台已实现范围，分别给尚未实现的版本、无法按标准识别当前版本，以及只有程序历史实测证据缺失但标准路径可用的情况；另检查官方规范修订、稳定/草案与实测结果的呈现归属。
- 预期结果：未实现版本报平台协议不支持，无法识别报协商或协议错误；不把 SDK 或 JSON-RPC 号当 ACP 版本，不进入等待用户决定兼容方案的流程。缺历史实测证据如实说明但不额外阻断已实现标准操作；草案不等于无规范，协商不等于真实执行通过，不擅自降低双版目标。

### CL-038 兼容升级沿标准路径且证据分版本

- 用例级别：L5
- 操作步骤：保留旧报告，登记未在报告中的兼容升级程序，按 ACP 重新协商并直接请求其已实现标准能力；请求前不提供平台兼容复验结论或用户兼容裁决，再独立记录开发/验收按影响复验的版本与范围。
- 预期结果：当前 ACP 标准能力及各自安全条件满足即沿标准路径使用，不因缺程序历史报告或平台兼容复验而先禁用，不强制增加厂商实现。旧报告只属原版本，未复验范围如实标注；标准调用结果不冒完整兼容性验收，证据追溯不成为运行时能力门槛。

### CL-039 升级后的不支持或协议错误如实报告

- 用例级别：L5
- 操作步骤：升级后的连接分别返回 Harness 不支持当前标准操作、与声明不符的业务错误和协议错误；尝试借用旧报告宣称新版通过，保留同连接的其他可用标准操作及其他兼容连接，并对照可能已有副作用但结果未知。
- 预期结果：如实呈现实际不支持或错误；协议错误按该版处置，可能已发生的副作用不自动重发。一次操作不支持不自动停用其他标准操作，不另建按厂商/程序版本停用能力的补偿规则、私有兜底或等待用户决定兼容方案的流程；旧证据保持原版本归属，不以旧报告伪称新版成功。

### CL-040 标准操作不支持直接报错且无平台兜底

- 用例级别：L5
- 操作步骤：对平台已实现的恢复或其他标准操作，分别给 Harness 声明不支持和实际返回不支持错误，检查立即响应及原生调用；另给仅无重放但输入/审批满足标准与安全条件的连接，并对照平台尚未实现该协议或操作。
- 预期结果：Harness 不支持则直接报告 ACP 所表达的不支持或实际错误，不等待用户兼容裁决、不另建平台准入/复验流程、不私有桥接、不改走替代会话、不伪报成功；平台未实现则明确报平台尚不支持，保留实际声明。其他标准能力独立使用；仅无重放提供当前连接模式及历史不完整/缓存丢失无法补回提示，权限、请求和资源安全规则仍成立。

### CL-041 版本矩阵不以模拟冒充真实

- 用例级别：L5
- 操作步骤：建立程序×协议×能力矩阵，对文档声明、运行协商、合同夹具、真实完整验收分别登记；核对 CL-030 的 Codex 首验。
- 预期结果：各证据不混称，未执行为 not-run；不假设每程序支持双版，不用旧探测或模拟代替真实执行/重放/恢复/树清理。

### CL-042 正常输出隐藏保存状态但内部保真

- 用例级别：L5
- 操作步骤：当前连接已有输出且无后续增量，首次订阅/重连/刷新读取；交错旧新读取响应，对照实际展示失败，不注入人为容量淘汰。
- 预期结果：首开即展示节点已有输出，正常不显示保存进度/提交版本；无旧预算截断或淘汰，旧响应不回退视图；真实失败报告原因，缓存不成为永久档案。

### CL-043 旧执行未证明停止时重连仍拒绝输入

- 用例级别：L5
- 操作步骤：先以独立模型入口演算，再用实际节点+协议对端复现：前台已派发无终态，依次断连、超时、新握手及仅中断已发送；每步在剩余名额内提交普通输入，对照无 Run 的 foreground unknown，并保留另一共享会话。
- 预期结果：旧活动/未知阻止下一条派发，但剩余名额可入队；不因新握手、超时或无 Run 解锁，不改变另一会话归属。标题中的“拒绝输入”历史含义替换为禁止派发；模型不替代节点或 L6。

### CL-044 资源收敛后仅显式新请求可继续

- 用例级别：L5
- 操作步骤：先模型后实际节点+协议对端：依次提供旧工作收敛、原生身份、唯一归属及必要恢复，逐一缺项尝试下一条派发；保留可证未发送旧项、可能发送项及失败挂起状态，另提交新输入。全部条件满足后分别在继续前/后观察。
- 预期结果：缺重新准入条件不派发；安全收敛后可证未发项遵循当前调度，挂起旧项须点击继续，新输入可独立优先。可能发送旧项不重发，旧结果未知不改成功、旧审批不复活。标题“仅显式新请求”不排除已受理且恢复可执行的未发送项。

### CL-045 原生确认停止路径必须证明恢复不会重派发

- 用例级别：L5
- 操作步骤：先模型后实际节点+协议对端，给完整可靠旧工作不再活动且恢复不重派发证据，与仅新握手、查询失败、错目标、可能重派发及归属冲突对照；保留失败挂起旧队列并提交新输入，另点击继续。
- 预期结果：只有完整可靠收敛及所需恢复才解除活动阻挡；旧项仍须继续，新输入不因旧项挂起被一并冻结。未知或错配不派发、不改旧副作用未知；替身不证明真实原生恢复保证。

### CL-046 真实异常退出到新一轮的 Windows 与 Web 路径

- 用例级别：L6
- 操作步骤：固定真实Windows/Harness/Web，输入后中断传输，旧资源仍存时另提交新输入；确认自有资源收敛、同原生身份、唯一归属及恢复后观察可证未发新项，并对失败挂起旧项显式继续，重试旧请求/审批。对照仍可能活动及资源不可核验。
- 预期结果：可入队不等于可派发；真实收敛后新输入按互斥/资源条件执行，挂起旧项须继续，可能发送项不重发、旧审批不复活。完整自有树清理且共享会话不强杀，缺真实依据记未执行。

### CL-047 无标准重放时仅发现能力且零产品派发

- 用例级别：L5
- 操作步骤：合同对端不提供标准历史重放，但分别满足创建、输入、审批和无重放恢复的标准与安全条件；从 Web/认证入口调用各自能力并统计实际 writer。另对照平台未实现能力。
- 预期结果：具备条件的操作实际派发，当前连接聊天可用；明显提示历史不完整及缓存丢失后无法补回。未实现能力单独拒绝，不扫描私有文件、不拼审计历史。标题“零产品派发”为保留追踪的历史语义，已被本断言替换。

### CL-048 相同标准能力共用路径且不设程序白名单

- 用例级别：L5
- 操作步骤：两不同名称/程序版本的合同对端在当前身份权限、请求去重、原生请求和资源安全条件满足时，提供相同已实现协议/标准能力且无程序历史报告；对照协议必备方法未额外广告、Harness 声明或响应不支持，以及对端声明平台尚未实现的能力。检查实际标准调用和未提供副作用探针。
- 预期结果：可用标准能力共用 ACP 路径，不要求程序版本白名单、额外平台能力准入矩阵/验证流程或协议未要求的可选标志；证据仅说明未实测范围。Harness 不支持直接报实际错误，平台未实现明确报平台尚不支持并保原声明；不私有兜底、不等待兼容裁决、不以输入/批准/删除等副作用探测能力，也不把安全条件包装为额外 ACP 能力证明。

### CL-049 完整历史流式传输与所有保留缓冲有界

- 用例级别：L5
- 操作步骤：无原生分页的对端全量流式重放超过旧视图/实体/节点/快照阈值的结构历史；混慢订阅、并发读取和页面参数，核对条目总数、原结构、完成边界及实际资源观测。
- 预期结果：全历史传输成本如实呈现，无旧内容上限拒绝、截断或淘汰；完成前不冒称完整，完成后来源/顺序真实，不写永久正文。标题“所有保留缓冲有界”不再要求平台内容预算，工程数量交接边界不能变相限正文。

### CL-050 部分中断解析失败及超预算不伪完整

- 用例级别：L5
- 操作步骤：分别在重放完成前断线、注入不合法结构、取消读取及实际来源不能继续；另提供超过旧32MiB帧/16MiB视图但当前协议可处理的合法内容；连接健康时并发输入审批，对照连接失效。
- 预期结果：真实中断/解析失败不伪完整，不重发输入；合法大内容不因旧预算失败。展示失败本身不取消工作或有效审批，连接失效按真实生命周期。标题“超预算”为历史语义，不再作为拒绝依据。

### CL-051 无跨加载稳定标识时重建代际而不按正文去重

- 用例级别：L5
- 操作步骤：两次重放只有各自可靠临时位置且含相同正文的不同项，两客户端并发查看，延迟旧响应并混入可关联/不可关联实时数据。
- 预期结果：同目标协调在途加载，新代际重建失效旧视图，旧响应不覆盖；不按正文/摘要去重，无法衔接说明限制。

### CL-052 重放完成不代替前台终态或恢复授权

### ACPI-R06 可取消边界、停止优先级与原任务收敛

**R06 取消来源澄清：**PendingReads future 暂停期间，同一原 reader 不会再次轮询 `receive_frame`，因此不得通过 peer Close 解除该暂停；取消统一由真实 Node stop 触发。Before/After-call transfer 和 InputAcceptedBeforeAck 均为一次性、无业务锁暂停点；测试触发 Node stop、等 control 非 ready 与原 future Drop 后释放 barrier，再由 `NodeProcessOwner::join_actual()` 读原 owner 结束。AfterCall finish 还要先用 preparation observer 确认真实 receipt 已 Registered，停止后释放 CPU barrier，并以 `storage.prompt_preparation_receipt().join()` 的 report 判实际 join。

- 用例级别：L5
- 操作步骤：每分支独立 Node fixture，四命令分别在 PendingReads 的 BeforeCall 和 AfterCall 一次性 barrier 暂停（无 owner/actor/lifetime 锁）；触发真实 Node stop，等 control 非 ready、原 connection 进入终止，释放 barrier，再确认 future drop、owner seal 和 connection/writer join，不出现取消后的后台补执行。finish BeforeCall 分支无 preparation receipt；AfterCall 分支用原 preparation observer 确认唯一 receipt 已 Registered，并暂停原 CPU；Node stop 后释放 CPU barrier，用 `storage.prompt_preparation_receipt().join()` 的 report 等待同一 task 实际 join，不再从旧 socket 查询。accept_data 返回后在 InputAcceptedBeforeAck 暂停，触发 Node stop；该 await 由原 ConnectionStop 取消，确认零 ACK、1001 与 owner 最终 seal。stop优先分支：在活 socket 先发送坏 ACPI，等 BeforeInputDispatch entered（已接收未 decode），触发真实 Node stop并等 control非 ready，释放barrier；确认处理前 lifecycle复核、dispatch次数0和唯一1001，不向已关闭连接发送第二帧。反向对照：不触发 stop，先让坏帧 dispatch并观察4400，随后停止Node。另由测试仅 seal 原 owner、保持 Node运行，分别发 status 与 Data，观察文本 product_not_ready 和 Binary 4400。
- 预期结果：取消不补执行、不重放、不伪造成功；BeforeCall零新增条目/receipt，AfterCall以真实原事实处理，结束后receiving=0、sealed=true；已移交内容仅有一个原receipt，observer取消不等于worker join。stop先于dispatch复核时1001、decode/owner dispatch次数零，不向已关闭socket再发帧；格式先被处理分支4400且只一个Close。运行中owner单独sealed时文本product_not_ready、Binary4400；Node/连接所有自有原任务实际join或明确unknown，不能以pending=0代签。

### ACPI-R07 FIFO、背压和精确预算回收

- 用例级别：L5（byte饱和分支另明确使用测试资源占用，不冒充网络自然填满）
- 操作步骤：FIFO 分支在 begin响应排空后设置原 `pause_next_write`（writer 已取出下一帧、actor gate前），发 Data 并等 writer entered，确认 ACK 已被取出：byte-used=32、queued=0、in-flight=1；发送 status 并等其 enqueue count 增加，释放 writer，以有序 helper 恰好读到 ACK 后 status 文本，等 send/drop 计数及预算归零。frame饱和独立 case 保持同一个首 ACK 在 writer pause 中，对最近块做256次真实幂等 Binary 重试，等每次 enqueue 观察累计达到 1 in-flight+256 queued，再发一次真实重试触发4429；随后释放 writer，断言 close ready 优先，已取出的 ACK可发送，未发送 queued ACK全部 drop且 permit归还。byte饱和独立 case 同样先暂停 writer，由 fixture 暂持原 byte semaphore 的 `MAX_OUTBOUND_BYTES - 31` permits（无假业务帧、无容量调整），WSS 发合法 Data 使32-byte ACK预算获取失败，观察4429；RAII释放 fixture permits，不要求伪造已发 ACK。
- 预期结果：FIFO分支只承诺成功 enqueue 的 ACK在后续文本前发送；byte permit包括in-flight并在send/drop后归还，writer取出时queued slot归还。frame分支证明1 in-flight+256 queued后下一次申请失败并close=4429；释放后因close优先不保证257个ACK均送达，queued ACK实际drop且预算回收。byte分支证明32-byte申请失败走4429，不外推自然慢网络已耗尽1MiB。两分支不另开sink，发送关闭都由原writer。
