# 节点共享队列与通用 ACP 设计

## Context

Q-001/Q-002、Q-003及当前Q-004已确认规则与原始要求见proposal。行为权威为八份specs，额外限制统一由acp-platform-constraints核对。已有节点、本地ACP客户端及分阶段管理/视图实现不代表完整闭环已交付；具体固定版本和有效检查见plan，历史证据保持原版本归属。

## Goals / Non-Goals

建立远端管理请求、节点受理和共享队列、本地协议所有者及原生工作之间的清晰边界；不新增模型或工具执行系统，不保存聊天档案。当前按用户要求先完成Q-004规格、用例和工作包的一致性修订；Q-001至Q-003的早期授权只保留各自历史范围，不允许据此跳过Q-004规划复核恢复实现。不操作实际用户数据库，不补签产品验收。

## Decisions

### 1. 节点受理是授权与责任交接点

远端管理通道先认证，再校验本次操作权限、目标和内容。节点登记请求ID及处理事实，重复提交只返回同一结果；未知旧登记ID不得重新当作新操作。队列编辑是新的管理操作，保留队列项身份及顺序，但绑定新的内容版本及本次编辑操作者。拒绝把不同内容塞回原提交ID。

受理后节点负责输入与审批交付，不依赖原操作者在线或再次授权；原actor仅保留审计归属。新的操作及每次读取仍检查当前操作者，撤销后停止该客户端读取及新请求，不取消其已受理工作。相比“持client_gate到首次发送”，本方案避免长队列依赖旧认证锁；既有控制通道撤销围栏只约束客户端交互，不作为已受理输入的发送许可。

### 2. 共享队列与活动工作分开

每原生目标只有一个节点队列和派发者，等待项最多三个，运行项及待插入项独立表示。队列无期限，只在节点运行期内存保存，浏览器变化不清理，节点重启不恢复正文也不专门提示丢失；必要去重及发送元数据独立保留。排队不立即占用前台Run唯一槽位，不以旧accepted-Run唯一索引拒绝后续入队。

节点按处理顺序决定入队、编辑、移除和取出；取消先处理则后续查不到不发送，发送先处理则取消或编辑失败。队列满时新草稿不能通过立即发送建立第四个等待项；现有项可优先。优先项请求被受理后，先中断旧前台并确认结束，再派发指定项，其他相对顺序不变。若发送/中断已可能发生，不凭本地队列删除声称收回字节。

可靠成功结束后自动发送下一条；可靠失败后挂起原队列，新输入优先执行，旧项须显式继续后恢复。达到上限、拒绝执行及普通取消的可靠结束保留原因并显示已停止，暂停旧队列；其恢复及立即发送例外以[执行规格](specs/session-execution/spec.md)的“非成功结束保留原因并暂停队列”为准。中断失败、活动未知或资源不可用时不冒险发送；恢复条件解决后仍保留旧项挂起状态，不阻止满足条件的新输入优先执行。输入受理不自动批准工具；真实权限请求单独裁决。

### 3. 发送事实与协议完成分开

节点内部顺序号只防止迟到回报覆盖新工作，不证明协议事件属于某输入。v1原prompt响应按该版终态语义处理；v2分别维护RPC到messageId的插入事实、按收到顺序的会话前台状态、可能的完成观察及Run结果。保留早到终态直到迟到插入响应处理，不能要求第二个idle；自发工作无法关联时保留未知，不把最近Run当归属依据。

在可证明旧前台不再活动且所有已发送输入的插入/拒绝状态已处理后，方可解除对应派发阻挡；Run副作用结果不能因此自动改成成功。普通idle快照不报告新完成。无法安全关联时提供核验、中断和受管理资源收敛出口，不能仅靠新握手解除。具体版本适配算法和原始帧合同须在编码前完成独立检视，不声称当前模型或WorkToken已完成此证明。

确定未发送可继续派发；已经可能接收而无法核验的动作不自动重发。浏览器重试只查节点事实。协议写入、插入和长时执行使用不同等待状态，模型慢不触发重复发送。若原生提供经验证的幂等机制，只有该机制的真实保证可支撑重试。

### 4. 协议接收与管理协调不循环等待

协议所有者独立消费reader和发送writer；接收循环不得等待命令持有的会话协调锁或原actor锁。队列操作仅在确定先后顺序的小范围内串行；load/replay/prompt、用户审批、数据库等待及完整执行不能持有会话互斥。协议事件及写意图采用有所有者的交接，控制处理不能排在普通输入后。

交接取消须使尚未发送项失效，已取出的发送在真正进入传输前重新核对队列版本/取消状态和原目标资源，不重验原actor；不能留下脱离owner仍会写入的潜伏任务。数量交接和未决协议关联可有明确工程边界，但不能借其重新设置正文或输出缓存容量上限。节点停止有取消及join顺序，Windows完整Job树清理与共享实例隔离分别验证。

### 5. 审批保存和节点交付

真实请求绑定来源、原生目标、连接及类型化RPC身份，Run仅在可靠关联时可选。未知主题或选项提示可安全通用展示，由人工选择原广告optionId；不以未知内容自动允许。保存唯一决定是交付允许的必要前提，提交失败或未知零允许；必要审批记录不降格为附加日志。

决定受理并保存后由节点交付，不因原审批者离线/撤销重新授权；仍在原连接核对真实待响应请求及原选项。原请求失效时抑制允许，安全响应与原决定分别记录。一次响应消费覆盖人工和安全路径，可能发送后不补发。会话取消范围遵循实际协商版固定官方合同，不以旧矩阵或前台idle推断全部请求失效。

### 6. 历史模式与有效配置

无重放也能接入，能力逐项报告；当前连接视图可共享，页面明显显示历史不完整及缓存丢失后无法补回。有重放按当前协商版读取；恢复上下文、重放和新输入分开，不按厂商构建读取器。

恢复/重放请求携带可信已授权的完整Client配置引用，包含该版支持的MCP与额外工作根。空集只能表达已确认的空配置，不能作为“保持不变”；外部来源未知时说明影响并限制该路径或取得所需授权，不解析私有文件。此处不建设平台工具系统。

输入正文、输出缓存、实体及视图不另设平台内容大小上限，旧16/128MiB、4096/32768条等不是新产品依据；32MiB帧、结构token等自设解析预算也不得被冒称协议上限或间接重建内容限制。既有管理控制通道的认证、帧及流控规则不自动取消，大正文交接不能用旧单对象/租约总量重新封顶。真正来自Harness/协议的限制须明确来源。

结构化展示将原始事件顺序与工具条目的更新分开：原始帧保留原序；具有可靠同一工具身份的后续进度和完成结果更新原工具视图，保留其首次出现位置及后文相对顺序，不因完成事件较晚就移动或追加重复条目。关联与展示的可观察规则由structured-history定义。

### 7. 必要状态、审计与时间

稳定登记身份、唯一派发、批准决定和资源责任是必要管理状态。附加审计失败或满额只告警，不以之全局停用；必要状态失效停止受影响新动作，并保留可验证的安全中断/拒绝/关闭。审计保留政策仍由management-audit负责，不驱逐受保护事实。

时间以节点为准，排队按节点处理顺序；无统一输入截止、回退锁定或持久时间水位。等待超时和耗时用单调计时器，节点校时不重排或过期队列。确有期限的其他认证凭据沿其自身规则，不自动改动归档节点认证。

### 8. 直接使用ACP能力，证据不作运行时准入

标准操作复用ACP协商、能力声明和方法，将Harness实际错误交给调用方；不另建能力准入矩阵、程序版本白名单、兼容复验阻塞或不支持时的用户裁决流程，不尝试私有桥接、替代会话或业务失败降版重发。平台未实现的操作明确报告平台不支持，不能伪称Harness不支持。规范允许的版本协商仍按ACP处理。

实测报告用于开发维护和发布验收的追溯，不进入标准调用的运行时资格判断。当前操作者权限、去重、原生请求有效性及资源归属仍由原有责任层核验；ReadTargetProof等内部对象只证明这些真实归属和生命周期，不承载额外的ACP能力验证。缺历史时的当前连接输出是独立视图，不把不支持的历史调用改写为成功。详细错误边界由harness-management单一定义。

### 9. 管理输入上传路由

管理上传的可观察行为由 `specs/management-input-upload/spec.md` 负责。上传确认只表示节点接收了数据，finish 只表示交给正文准备服务；只有 ready 才返回 bodyId，后续登记、消费及 Harness 执行分别报告自己的事实。原有队列、受理授权及正文仅内存规则保持由执行规格负责。

正常产品启动在开放 HTTPS/router 前，从同一个原 OwnedNodeSessionServices 构造不可拆分的管理服务集合，包含队列读取、队列管理及上传。ManagementService 只一次发布该集合；构造器不接受分别来自不同节点的三个句柄。安装校验原 SocketViewAuthority 身份，失败使产品启动失败；仅控制面模式没有集合，明确报告 product_not_ready。

认证成功后，attachment 打开并持有该连接唯一 UploadOwner。四条上传命令通过原 PendingReads 监督，二进制数据经原 reader 调用该 owner；不按请求建立新 owner，不新增脱离连接的命令任务。连接结束由原 SocketLifetime 封存未移交数据；已经 finish 的准备工作仍由原节点准备服务监督和关闭，观察者取消不冒充实际任务 join。

UploadOwner 的现有业务错误能够直接投影为上传状态；其内部当前 actor 复核还可能产生撤销或认证存储失败。路由适配必须保留这三类来源，而不是把全部错误压成 invalid_request：业务错误按上传表处理，撤销只关闭为 4410，认证存储失败只关闭为 4500。该适配不改原有的正文准备、已受理队列授权或源读取语义，也不以失败后的再次查询改写原错误。

完整 ACPI magic 决定上传帧分类，其他二进制继续原共享视图控制路径。处理前已观察到节点停止时优先 1001，随后不解码和调用上传业务。运行中上传业务错误以 4400 结束且无 ACK/JSON；认证撤销为 4410，认证存储复核失败沿既有 4500，传输和出站预算超限为 4429。停止与格式错误未确定先后的竞态不虚构固定顺序。

成功接收数据后，32 字节 ACK 使用原出站队列、字节许可和唯一 writer，与文本结果按成功入队顺序发送。Binary 与文本共用发送前 actor gate；撤销先提交时未通过 gate 的 ACK 不发送。writer 已取出的帧仍占字节许可，发送或丢弃才归还。共享视图分支保持自己的所有权和发送检查。

测试暂停点仅用于观察原调用的确定边界，不跨上传表、actor、lifetime 等业务锁等待，不创建替代 owner、发送通道或业务帧。真实 TLS/WSS 的 ACPI-R01—R08 覆盖正常、错误、关闭、撤销、背压和取消；正文准备状态与原准备任务 join 分别取证。用例未执行或独立检视未通过时，不把设计合入当作能力交付。

数据接收后的取消、命令调用前后的取消均由原节点生命周期停止触发；同一原 reader 在 pending future 暂停时不再承担读取 peer Close 的职责。测试的首次服务构造失败发生在 listener/router 创建之前，随后使用原 lifecycle owner、preparation shutdown report 和地址不可连接事实分别证明关闭与未发布，不以本地计数器代替实际 join。

## Risks / Trade-offs

- [节点重启丢失未发正文] → 用户已选择不跨重启保存、不专门提示；元数据仍不能引发旧输入补发。
- [无重放或缓存生命周期结束后前文不可读] → 明显历史限制提示；其他实际能力独立可用。
- [没有平台正文/输出容量限额] → 接受该产品取舍，不偷偷恢复旧预算；真实分配/传输故障如实报告，不宣称无限物理资源。
- [v2会话级活动不能唯一归因] → 保留事实与未知，独立核对帧乱序；不能虚报每条输入都有原生执行ID。
- [旧合同及已开发代码不符新规则] → 明确停用冲突子合同，阶段用例和代码差异重新冻结审查，不外推旧通过报告。

## Migration Plan

本次Q-004文档修订不迁移实际数据。以当前固定源码和迁移合同为基线，保留身份、信任、撤销、旧管理和正文数据，不自动删除旧表或列。旧schema中的request_epoch/time_floor等可留作不生效历史字段，不继续驱动新输入；后续DDL与回滚仍需独立检视。节点启动不恢复队列正文，已发生/可能发送事实保守核验。

## Implementation Gate

先完成Q-004规格、CL-117–123、工作包和任务映射的独立一致性核对，并由用户明确放行，再恢复实现或正式验收；Q-003“再继续实现”的早期表述只保留历史范围。未完成快照和旧门槛保留各自范围，不以旧规范的准入或90天默认值继续编码。后续工程合同与真实验证仍按plan/tests/tasks执行，不把开发验收要求变成产品额外能力门槛。完整Node/WSS/Web及真实Harness验收未完成，不能以文档更新或局部检查补签。


## Q-002 补充：连接寿命与失败挂起

删除当前客户端累计4096个已见Harness请求ID上限，不能因第4097个及后续合法请求失效连接；此次仅删除累计寿命阈值，真实请求身份、单次回复及现有同时未决控制保持。原始ID记录不以清理复活旧请求，本次不增加更大替代阈值。

执行失败时挂起原队列并保留项及顺序；后续新输入在前台/资源允许时直接优先执行，新输入成功不自动恢复旧项。点击继续后原项才重新加入可执行队列，不复制、重新授权或抢占当前新输入；新输入本身若需等待，仍遵守包含挂起项的三个未发送总名额，不建立第四等待项。正常队列满额新草稿规则保持，仅失败挂起后可直接执行的新输入走优先路径。

本轮代码仅移除累计请求阈值及回归测试；完整节点队列实现仍待后续阶段，不能将规则修订当作已交付。
