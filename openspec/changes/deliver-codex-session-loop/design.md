# 节点共享队列与通用 ACP 设计

## Context

本轮 Q-001 已确认规则及原始要求见 proposal。行为权威为八份 specs，额外限制统一由 acp-platform-constraints 核对。当前已有节点、本地 ACP 客户端、schema4 及部分管理/视图实现；它们包含旧签名期限、正文预算和派发再验权，不代表新规则已实现。历史证据保持原版本归属。

## Goals / Non-Goals

建立远端管理请求、节点受理和共享队列、本地协议所有者及原生工作之间的清晰边界；不新增模型或工具执行系统，不保存聊天档案，Q-001不改代码；Q-002仅实现累计请求阈值删除，不迁移真实数据库或补签队列产品通过。

## Decisions

### 1. 节点受理是授权与责任交接点

远端管理通道先认证，再校验本次操作权限、目标和内容。节点登记请求ID及处理事实，重复提交只返回同一结果；未知旧登记ID不得重新当作新操作。队列编辑是新的管理操作，保留队列项身份及顺序，但绑定新的内容版本及本次编辑操作者。拒绝把不同内容塞回原提交ID。

受理后节点负责输入与审批交付，不依赖原操作者在线或再次授权；原actor仅保留审计归属。新的操作及每次读取仍检查当前操作者，撤销后停止该客户端读取及新请求，不取消其已受理工作。相比“持client_gate到首次发送”，本方案避免长队列依赖旧认证锁；既有控制通道撤销围栏只约束客户端交互，不作为已受理输入的发送许可。

### 2. 共享队列与活动工作分开

每原生目标只有一个节点队列和派发者，等待项最多三个，运行项及待插入项独立表示。队列无期限，只在节点运行期内存保存，浏览器变化不清理，节点重启不恢复正文也不专门提示丢失；必要去重及发送元数据独立保留。排队不立即占用前台Run唯一槽位，不以旧accepted-Run唯一索引拒绝后续入队。

节点按处理顺序决定入队、编辑、移除和取出；取消先处理则后续查不到不发送，发送先处理则取消或编辑失败。队列满时新草稿不能通过立即发送建立第四个等待项；现有项可优先。优先项请求被受理后，先中断旧前台并确认结束，再派发指定项，其他相对顺序不变。若发送/中断已可能发生，不凭本地队列删除声称收回字节。

可靠成功结束后自动发送下一条；可靠失败后挂起原队列，新输入优先执行，旧项须显式继续后恢复。中断失败、活动未知或资源不可用时不冒险发送；恢复条件解决后仍保留旧项挂起状态，不阻止满足条件的新输入优先执行。输入受理不自动批准工具；真实权限请求单独裁决。

### 3. 发送事实与协议完成分开

节点内部顺序号只防止迟到回报覆盖新工作，不证明协议事件属于某输入。v1原prompt响应按该版终态语义处理；v2分别维护RPC到messageId的插入事实、按收到顺序的会话前台状态、可能的完成观察及Run结果。保留早到终态直到迟到插入响应处理，不能要求第二个idle；自发工作无法关联时保留未知，不把最近Run当归属依据。

在可证明旧前台不再活动且所有已发送输入的插入/拒绝状态已处理后，方可解除对应派发阻挡；Run副作用结果不能因此自动改成成功。普通idle快照不报告新完成。无法安全关联时提供核验、中断和受管理资源收敛出口，不能仅靠新握手解除。具体版本适配算法和原始帧合同须在编码前完成独立检视，不声称当前模型或WorkToken已完成此证明。

确定未发送可继续派发；已经可能接收而无法核验的动作不自动重发。浏览器重试只查节点事实。协议写入、插入和长时执行使用不同等待状态，模型慢不触发重复发送。若原生提供经验证的幂等机制，只有该机制的真实保证可支撑重试。

### 4. 协议接收与管理协调不循环等待

协议所有者独立消费reader和发送writer；接收循环不得等待命令持有的会话协调锁或原actor锁。队列操作仅在确定先后顺序的小范围内串行；load/replay/prompt、用户审批、数据库等待及完整执行不能持有会话互斥。协议事件及写意图采用有所有者的交接，控制处理不能排在普通输入后。

交接取消须使尚未发送项失效，已取出的发送在真正进入传输前重新核对队列版本/取消状态和原目标资源，不重验原actor；不能留下脱离owner仍会写入的潜伏任务。数量交接和未决协议关联可有明确工程边界，但不能借其重新设置正文或输出缓存容量上限。节点停止有取消及join顺序，Windows完整Job树清理与共享实例隔离分别验证。

### 5. 审批保存和节点交付

真实请求绑定来源、原生目标、连接及类型化RPC身份，Run仅在可靠关联时可选。未知主题或选项提示可安全通用展示，由人工选择原广告optionId；不以未知内容自动允许。保存唯一决定是交付允许的必要前提，提交失败或未知零允许；必要审批记录不降格为附加日志。

决定受理并保存后由节点交付，不因原审批者离线/撤销重新授权；仍在原连接核对真实待响应请求及原选项。原请求失效时抑制允许，安全响应与原决定分别记录。一次响应消费覆盖人工和安全路径，可能发送后不补发。会话取消范围遵循实际协商版固定官方合同，不以旧矩阵或前台idle推断全部请求失效。

### 6. 历史模式与有效配置

无重放也能接入，能力逐项报告；当前连接视图可共享，页面明显显示历史不完整及缓存丢失后无法补回。有重放按当前协商版读取；恢复上下文、重放和新输入分开，不按厂商构建读取器。

恢复/重放请求携带可信已授权的完整Client配置引用，包含该版支持的MCP与额外工作根。空集只能表达已确认的空配置，不能作为“保持不变”；外部来源未知时说明影响并限制该路径或取得所需授权，不解析私有文件。此处不建设平台工具系统。

输入正文、输出缓存、实体及视图不另设平台内容大小上限，旧16/128MiB、4096/32768条等不是新产品依据；32MiB帧、结构token等自设解析预算也不得被冒称协议上限或间接重建内容限制。既有管理控制通道的认证、帧及流控规则不自动取消，大正文交接不能用旧单对象/租约总量重新封顶。真正来自Harness/协议的限制须明确来源。

### 7. 必要状态、审计与时间

稳定登记身份、唯一派发、批准决定和资源责任是必要管理状态。附加审计失败或满额只告警，不以之全局停用；必要状态失效停止受影响新动作，并保留可验证的安全中断/拒绝/关闭。审计保留政策仍由management-audit负责，不驱逐受保护事实。

时间以节点为准，排队按节点处理顺序；无统一输入截止、回退锁定或持久时间水位。等待超时和耗时用单调计时器，节点校时不重排或过期队列。确有期限的其他认证凭据沿其自身规则，不自动改动归档节点认证。

## Risks / Trade-offs

- [节点重启丢失未发正文] → 用户已选择不跨重启保存、不专门提示；元数据仍不能引发旧输入补发。
- [无重放或缓存生命周期结束后前文不可读] → 明显历史限制提示；其他实际能力独立可用。
- [没有平台正文/输出容量限额] → 接受该产品取舍，不偷偷恢复旧预算；真实分配/传输故障如实报告，不宣称无限物理资源。
- [v2会话级活动不能唯一归因] → 保留事实与未知，独立核对帧乱序；不能虚报每条输入都有原生执行ID。
- [旧合同及已开发代码不符新规则] → 明确停用冲突子合同，阶段用例和代码差异重新冻结审查，不外推旧通过报告。

## Migration Plan

本轮不迁移。先冻结当前源码、schema4及未提交工作，逐阶段提出新的请求登记、队列元数据及派发布局；保留身份、信任、撤销、旧管理和正文数据，不自动删除旧表或列。旧schema中的request_epoch/time_floor等可留作不生效历史字段，不继续驱动新输入；新DDL与回滚需另行精确定义并独立检视后实现。节点启动不恢复队列正文，已发生/可能发送事实保守核验。

## Implementation Gate

Q-001是规格/规划修订；Q-002仅累计请求阈值删除有窄代码回归。完整队列、迁移和真实Harness验收仍未执行，旧规划报告不作为Q-002覆盖依据。tests.md是修订候选，plan/tasks列明重基准与实现工作；旧任务完成只保留历史范围。编码前必须固定队列状态、原始帧终态关联、有效配置和迁移合同，并取得独立检查。


## Q-002 补充：连接寿命与失败挂起

删除当前客户端累计4096个已见Harness请求ID上限，不能因第4097个及后续合法请求失效连接；此次仅删除累计寿命阈值，真实请求身份、单次回复及现有同时未决控制保持。原始ID记录不以清理复活旧请求，本次不增加更大替代阈值。

执行失败时挂起原队列并保留项及顺序；后续新输入在前台/资源允许时直接优先执行，新输入成功不自动恢复旧项。点击继续后原项才重新加入可执行队列，不复制、重新授权或抢占当前新输入；新输入本身若需等待，仍遵守包含挂起项的三个未发送总名额，不建立第四等待项。正常队列满额新草稿规则保持，仅失败挂起后可直接执行的新输入走优先路径。

本轮代码仅移除累计请求阈值及回归测试；完整节点队列实现仍待后续阶段，不能将规则修订当作已交付。
