# 通用 ACP 会话闭环，以 Codex 首验

状态：待实现文档齐备；旧快照独立方案结论见 review.md，本轮修订检视另记总体报告，产品未实施；上游真实交付和能力探测门禁仍需满足。

## Why

当前分支没有产品实现。为按重设计建立可独立验收的交付闭环，需要打通 Codex 原生会话执行闭环，避免仅交付孤立模块而没有可观察结果。

## Success Criteria

> 同意，那就先建立整体能力地图及依赖关系，再按可独立验收的闭环拆成多个 change。

> 其他九项也补齐文档到待实现状态吧

### 硬约束与非目标

- 以[重设计 §2.2–§6.1、§6.3–§7.3、§10.2](../../../docs/HARNESS_CONTROL_PLANE_REDESIGN.md)为本闭环依据；采用新架构、不兼容旧系统，其他适用的全局约束仍然有效。
- 先建立最小可用操作界面与管理接口；不以全部客户端形态作为本 change 的交付承诺。
- 本轮补齐待实现文档，不开始产品实现，不将规划或模拟结果写成已提供能力。首期限定 Windows 节点 + Web，App 后续。

### 本 change 的成功判据（待详细规格转成场景）

- SC1：登记 Harness 与工作目录，创建会话、提交输入、展示结构化输出、处理审批及取消，保存历史，释放后原生恢复继续输入。
- SC2：固定 Codex 与适配器版本，真实验证执行、审批唯一裁决、取消完成信号、页面断开继续运行、正常释放与恢复；异常不重发，保存失败不虚报成功。
- SC3：建立真实构建及适用检查，完成独立用例/方案检视和交付验收；记录未验证项及实质限制。

## What Changes

- 2026-10-29最新页面要求：正常输出不显示保存进度/状态或提交版本，仅异常时显示错误；内部版本事实、持久化与失败停止规则不变。对应structured-history、design及验收预期同步修订，不实施产品代码。

- 建立通用 ACP 客户端和版本兼容边界，以 Codex 作为首个真实验收对象；保留 `deliver-codex-session-loop` 目录 ID，不把该 ID 当成架构边界。
- ACP v1/v2 均纳入兼容目标；具体规范、版本标识、协商方式与发布状态在编码前核实，分别提供合同及真实证据，不能将兼容设计当成已支持。
- 标准能力按协议版本及协商能力选择，不按厂商名分支；DeepSeek、ZCode 后续仅承担接入配置和兼容性验收。不兼容时明确报告影响及可选方案，等待用户决策，不自行写私有桥接或降低产品要求。
- Agent 升级触发影响分析和兼容性复验，不自动触发代码适配或抹去旧版本证据。
- 登记 Harness 与工作目录，创建会话、提交输入、展示结构化输出、处理审批及取消，保存历史，释放后原生恢复继续输入。
- 同步负责上述行为的设计、规范、测试、配置与操作文档；不复活旧系统合同。

## Capabilities

### New Capabilities

- `harness-management`：Harness 定义、版本、能力协商与实例所有权。后续文件为 `specs/harness-management/spec.md`。
- `workspace-registration`：工作目录登记、解析与可用性。后续文件为 `specs/workspace-registration/spec.md`。
- `session-execution`：受理、请求防重复、前台执行互斥、派发和取消。后续文件为 `specs/session-execution/spec.md`。
- `permission-approvals`：请求有效性、唯一裁决、交付与失效。后续文件为 `specs/permission-approvals/spec.md`。
- `structured-history`：结构化条目、源顺序、有界缓存、合并保存与失败处理。后续文件为 `specs/structured-history/spec.md`。
- `native-session-recovery`：原生绑定、正常释放、原生恢复与异常事实。后续文件为 `specs/native-session-recovery/spec.md`。
- `management-audit`：管理动作、操作者、依据与结果的审计。后续文件为 `specs/management-audit/spec.md`。
