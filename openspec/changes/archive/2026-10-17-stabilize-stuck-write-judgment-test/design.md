# Design

## Context

- 被改的两条用例：`crates/server/src/sync/conn/tests.rs` 的 `a_stuck_write_still_lets_the_session_judgments_run`（约 2376 行）与 `crates/server/src/node_link/conn/tests.rs` 的同名用例（约 2970 行）；后者的存在性由前者注释里的「与 `node_link/conn/tests.rs` 的同名 helper 逐条同构」承诺约束。
- 命题（对应 `sync-device-auth` 与 Node Link 同族要求的场景「写路径有期限且写卡住时判据仍被检查」）：**对端一个字节都不读、出站队列被顶到饱和时，会话仍会被静默判定收尾**。
- 判别结构：注入 `SILENCE = 600ms` 与写期限/看门狗窗口 `WRITE_WINDOW = 30s`，用 `OutboundPressure::spawn_with_filler` 把队列顶饱和，再断言连接在有界预算（`SILENCE + 11_400ms` = 12s）内被收尾——**由「预算远小于写窗口」推断收尾只可能来自静默判定**。
- 合法路径的构成（作者注释记录）：静默判定（第 2 拍 tick，tick = 500ms）≈1.0–1.1s + 关闭路径按预算走满的排空与 join（各 2s）+ 收尾 ⇒ 本机 ≈3.5s、CI 慢跑器 7.54s。
- 观测到的抖动：2026-10-16 两次超时 16.30s / 29.68s，均出现在同一次 push 与 PR 事件**各触发一条完整工作流、两条并行**的负载下；重跑即绿。29.68s 已经贴到 30s 写窗口。
- 同文件里另两个 `assert_eventually_within` 调用点（`GRACE + 8s`）走的是「写任务到期立刻唤醒 `select!`」的无 tick 路径，同一天同负载下未抖动 ⇒ 不在本变更。
- 两条**不可用**的替代路线：
  - tokio 时间冻结（`start_paused` + `advance`）：本用例跑在**真实 TCP** 上，冻结时钟会让 I/O 就绪不再推进。
  - 直接断言收尾成因：`Ending`（`Close(code, reason)` / `TransportClosed(reason)`）是 `session.rs` 的**内部**枚举，registry/handle 不记录它；server 测试也没有日志捕获设施（`crates/app/src/logging.rs` 那套手写 `Subscriber` 只在 app 侧）。而且本用例下服务端的**写半边是卡住的**，close 帧根本发不出去，客户端侧也读不到成因。

## Goals / Non-Goals

**Goals：**

- 让该用例的余量足以吸收 CI 负载翻倍，同时**不削弱它证明的命题**（收尾仍远早于写窗口）。
- 两个同构用例同批改，保持对称。

**Non-Goals：**

- 不改产品代码、不给产品加「收尾成因」可观察点、不给 server 测试加日志捕获设施。
- 不改 CI 触发方式与并发策略（见 Open Questions）。
- 不动另外两处 `GRACE + 8s` 预算（无实测抖动，改它属无据的顺手改动）。

## Decisions

**D1 选「放大余量」，不选「改成不依赖墙钟」。**

命题本身是**上界命题**（「不会被无限期拖着」），它的判别力来自「预算 ≪ 写窗口」这层关系，而不是来自精确耗时；因此放大两个数字即可保住命题。两条替代路线各有不可接受的代价（见 Context 最后一条）：冻结时钟与真实 TCP 不兼容；断成因需要新产品面或新测试脚手架，收益不成比例。

代价如实登记：失败时的诊断延迟从最多 12s 变为最多 60s（正常情况下用例仍在 ≈3.5s 内结束——预算只在失败路径上才被等满）。

**D2 三个数字必须一起改：断言预算、注入的写窗口、记录它们的注释。**

只抬预算而不抬写窗口会制造新的自相矛盾：29.7s 这类实测值会落进「预算允许、但已经跨进 30s 写窗口」的区间，那时用例变红的原因将不再是「静默判定没生效」而是「写期限先收尾」——一种**误报**。

**D3 取值：写窗口 30s → 300s，预算 12s → 60s。**

- 60s ≈ 2× 已观测最差实测（29.7s），≈17× 本机合法路径（3.5s）；
- 60s vs 300s = 5× 自身间距，判别力（预算 ≪ 写窗口）比改动前（12s vs 30s = 2.5×）更强；
- 写窗口只承担「必须远在预算之外」这一个角色，抬高它不改变用例证明的事。

**D4 两个孪生用例同批改。**

只改一侧会留下不对称，而另一侧会在下一次同样的负载下以同样的方式红；两个文件都在 `crates/server/src/**`，属同一写范围。

## Risks / Trade-offs

- **失败诊断变慢**：最坏 60s 才报错。取舍：该失败是罕见路径（今天两次，均由重复工作流造成），慢比误报可接受。
- **负载再翻倍时 60s 也可能不够**：届时应按新的实测再抬。5× 的自身间距保证它不会退化成「与写窗口打架」，因此调整是安全的、可延后的。
- **会不会掩盖产品回归**（合法路径真的变慢）？本用例只断言「远早于写窗口」；写期限路径的真实量级由同文件的 `GRACE + 8s` 对照用例守着。因此放大余量不掩盖那类回归。

## Open Questions

- CI 的重复执行（同一次 push 同时触发 `push` 与 `pull_request` 两条完整工作流）是这次负载翻倍的直接来源；是否加 `concurrency: cancel-in-progress` 属独立议题，可能顺带消灭这类偶发——本变更不动 CI 配置。
