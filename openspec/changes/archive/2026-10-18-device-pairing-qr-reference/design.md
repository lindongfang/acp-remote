# Design

## Context

动机与用户已确认边界见 proposal.md。当前代码已实现 PWA 的完整设备 `#data=` 自动认领、裸 `/pair` 配对码 lookup、主机证明与批准身份校验；原生相机、`.native.ts` 平台实现尚未交付。现有网页 lookup 成功即消耗码；身份模块的秘密与码集中驻留内存。CLI 的在途修改已将 Braille 改为固定黑白实心半块，不能回退这些修改或覆盖前端主题工作。

已核实的权威约束：身份合同 §4.3 允许拒绝后为轮询保留秘密，但取回资格并不随之保留；有效期默认/上限 300 秒且可缩短；现有 lookup 和认证实现要求 canonical origin。Sync 文档关于原生无 Origin 的候选描述不代表已实现，本变更明确选用携带目标 Origin 的原生配置。

## Goals / Non-Goals

**Goals:**

- 让短二维码的带外公钥锚、取回凭据、配对秘密分别建模，接入原状态机而不复制信任创建流程。
- Rust 与 TypeScript 以共享 manifest/fixture 固定编码、取回、指纹和错误边界；浏览器不启用 App 取回器。
- 无数据库迁移、无新 crate、无新增密码算法或云依赖。

**Non-Goals:**

- 不实现 Android/iOS App、相机、深链、安装分发或原生 keystore；共享消费方的测试不能被描述为原生产品验收。
- 不改变 Node Link、ACP、已有业务命令与设备撤销规则；不新增设备 scope。
- 不以客户端名称或 Origin 请求头作为授权证明；PWA 不使用该接口是产品行为，服务端仍按凭据验证，不能声称能阻止自定义客户端调用。

## Decisions

### D1：短地址格式与尺寸预算

固定格式为 `https://<origin>/pair#q2=<base64url>`；外层 HTTPS URL 必须无 userinfo、无 query、无额外路径/重复片段键。payload 精确为 `[0x02 | qrToken(32) | hostKeyFingerprint(32)]`，无填充 base64url 共 87 个 ASCII 字符；拒绝其它版本、长度和非规范编码，不尝试旧设备 JSON。`https://faraday.tail74842e.ts.net:8765/pair` 长 43，加 `#q2=` 4 和 payload 87，总长 134；这一测试地址限定 <=150 字节，不能承诺任意长度合法主机名都 <=150。L 级加四模块白边预计最多 58 列×29 行，落地以真实编码器测试为准；保留实心黑白绘制、白边与窗口提示。

采用 C 而不是完整二进制包，是用户在尺寸、安全锚与一次额外请求之间的选择。不能回到点阵绘制来满足尺寸预算，也不截断指纹。

### D2：使用已有公钥指纹语义

指纹为 `SHA-256(规范 65 字节 SEC1 未压缩 P-256 公钥)`，与 core 的既有指纹一致；二维码保存 32 字节原始摘要，非 64 字符 hex。Rust 的公钥校验与指纹入口沿用既有领域类型，协议模块不反向依赖 core；TS 使用平台标准 SHA-256，固定向量保证一致。不改用 JWK 指纹、证书指纹或截断摘要。公钥必须先满足既有长度和曲线合法性检查，再匹配完整指纹。

指纹只绑定主机公钥，不单独认证其他返回字段；其余字段受可信 HTTPS、来源/格式/有效期检查和现有 claim/status 证明约束。匹配指纹后仍必须验证 hostProof、批准响应的同一 hostId/公钥和每次 WSS challenge-response。禁止把本方案描述为不依赖 TLS 或不信任页面代码。

### D3：凭据及资料的单一生命周期

增加语义明确、Debug 脱敏且不实现 Display 的扫码取回凭据值对象。设备创建时由密码学随机源独立生成 qrToken 与 pairingSecret，各32字节；网页码继续从 pairingSecret 按既有规则派生。凭据只绑定唯一设备配对，创建冲突时重新生成，不能两配对共享凭据。

`identity-auth` 在同一次设备创建操作中登记 qrToken 与已有 PairingMaterial，并集中清理反查索引；不新增普通 SQLite 字段，不可由持久化摘要恢复。创建、旧材料替换、reset_memory、过期、证明失败失效、拒绝、成功认领与首次认证等路径必须核对取回资格。成功认领可立即移除 qrToken 索引；为幂等 claim/status 保留 pairingSecret 不重新开放索引。

该资料在一次配对内保持不变。服务端若检测到配置的 canonical origin 或主机身份与创建时绑定不同，失败关闭并要求重新配对，不能让旧二维码返回当前另一身份。取回后尽快清除客户端 qrToken，配对资料只进入私有会话状态。

### D4：单独取回接口，复用资料校验而非码消耗流程

新增 `POST /sync/v1/pairing/qr-lookup`：

```json
{ "protocolVersion": 1, "qrToken": "<32-byte-unpadded-base64url>" }
```

成功 200 返回现有配对码 lookup 的七字段结构。只有 `created`、未过期、未被内存标记失效且来源/Host/身份绑定一致时可成功；不消耗码、不消费 qrToken、不创建配对请求或信任。与码 lookup 共享字段验证/资料装配，但不能调用码的 consume 路径。未知键、类型/编码/长度错误及不可取回状态统一 `401 pairing.qr_invalid`；沿用协议错误信封，登记到 errors 唯一机器词表及对应 enum/fixture。415 不作为新规则：非 JSON 沿用现有 400，超限 413、方法 405、网络 Host 拒绝沿用现有接入层行为，429 带 Retry-After。

请求上限 16 KiB；每真实来源地址 10 次/分钟，独立于码 lookup、claim；不增加配对 proof 失败计数，不建立无界凭据失败缓存。所有处理器和预处理响应带既有四安全头与 no-store，不记录请求/响应正文。

### D5：并发交付边界与线性化

“认领后不再取回”指取回资格判定必须与认领的权威状态有可解释先后，不能只检查“内存有秘密”。先验证来源，再做有界凭据查找，读取对应持久配对状态，并核验内存失效及身份绑定后交付；在身份层和存储边界保持既有依赖方向，不让 adapter 直连 SQLite。

取回的成功必须能对应认领生效前的一次有效权威读取；认领提交后开始的取回不可成功。已经在认领前获准的在途响应可能在认领后到达，不能承诺撤回已经发出的字节。用可控并发屏障验证该先后，以及拒绝、过期、失效与清理交错；不以进程内秘密存在性替代持久状态。状态检查所需的现有只读端口应优先复用；若必须改变 core 端口，回到计划修订，不能在实现中临时扩展依赖或存储合同。

网页码与 qrToken 可以分别取回，但只争用同一个 claim 状态机。相同内容 claim 重试返回原结果，不同身份冲突；认领后客户端复用已得资料进行幂等重试，不回头调用 qr-lookup。

### D6：客户端边界与重试默认值

PWA `/pair` 无片段只显示配对码输入；`q2=` 在任何业务请求、持久化、遥测或 UI 载荷回显之前被替换历史清除，再显示固定 App 指引；旧设备 data 格式同样清除后提示不支持。不同载荷/入口错误仍用固定文案。节点完整二维码读取仍隔离保留，设备移除不能误删它的解析器。

原生消费方合同由共享协议测试/模拟调用方验证：固定扫码 URL 的 canonical origin，所有 HTTPS 请求与 WSS 显式使用同一目标 Origin，HTTP 重定向直接失败，不根据响应重定向或 public key 改写目标。Origin 是绑定输入而非客户端真实性证明。

暂时网络故障、超时及 502/503/504 可用相同请求最多尝试3次，总墙钟预算30秒（含请求超时/等待）；普通退避500ms、1000ms，单请求最长8秒。429 按 Retry-After，超剩余预算则停止；第一次取得 expiresAt 后同时受其约束。未取得资料前虽不知道实际到期时间，仍有本地总预算，服务端每次执行真实有效期检查。认证、格式、来源、指纹错误、其它非暂时失败立即停止。预算/具体常量可在原生交付前另行调整，但此轮实现测试使用这些明确上界。

本次可新增供未来原生消费的纯协议解码与重试策略模块，但必须有测试调用方，不能接到 PWA 页面或伪造 native 平台能力。App 相机/界面/安全存储留后续；PWA 码 lookup 仍一次性、失败固定文案、不自动重试。

### D7：权威文档与术语归属

实施 WP1 新增 ADR（预计0012，核对编号）记录 C 的权衡、设备格式完全替换与 PWA/App 边界；ADR-0010 标注其设备二维码结论被新 ADR 取代，网页配对码决定仍有效。术语表增加“扫码取回凭据”，区别于配对码和配对秘密；只写定义，不放 wire 布局。

Sync 协议拥有 QR、端点、原生 Origin 与失败/限额合同；身份合同拥有内存材料及状态机；前端设计拥有 PWA 行为和原生仍后续的阶段；产品/安全文档只概述并链接权威定义。本地管理协议说明 pairingUrl 新含义与 CLI 提示。按需更新模块职责概要但不增加模块或端口。机器资产与 Rust/TS 共享向量同一工作包交付。

## Risks / Trade-offs

- [取回新增一次网络请求且凭据也是敏感材料] → 可信HTTPS、内存/日志边界、短有效期、有限重试；凭据泄露与完整旧二维码泄露一样可能引发抢先认领，本机确认继续保留。
- [指纹不保护被整体替换的二维码或失陷的 App/页面] → 保持原带外信任假设，不宣称消除此风险。
- [原生尚未交付，终端二维码暂不能用于现有产品扫码配对] → 在二维码图案前打印 `二维码：` 标签；PWA 码配对完整可用，不以协议模拟测试代替真机验收。
- [拒绝后秘密仍驻留容易误开放取回] → 同时检查权威状态和内存失效，测试全部状态和重启。
- [旧前端缓存仍有 data 自动认领代码] → 协调部署、刷新静态资源/服务工作线程，不能只改服务端生成器；不许以服务端能区分客户端 UI 作为保护。
- [工作区在途主题及 CLI 修改] → 实施前记录差异为基线，patch 只交付本变更新增内容，独立检视核对不回退既有修改。

## Migration Plan

1. 以本变更增量规范为目标，先同步新 ADR 与权威协议/安全/前端合同及共享 schema/fixture，再串行接入身份、服务端、CLI、PWA。
2. `device.pair.begin` 返回键保留但 pairingUrl 内容破坏兼容；QR 自带版本，HTTP 消息仍为 protocolVersion 1，不以 WSS feature negotiation 判断未认证 QR 支持。旧设备 data 生成、产品解析、旧样例说明全部退出；节点 data 不动。
3. 前端静态资源与 Daemon 同一版本发布并验证旧缓存刷新；已有配对身份、会话及数据库不迁移。部署重启使未完成配对材料失效，提示重新生成配对码/二维码，不能读取旧摘要恢复。
4. 整体回滚 Daemon 与前端到配套旧版本，重启后重新生成未完成配对；不承诺新旧二维码跨版本继续可用，不保留双栈解码回退。不撤销既有已批准信任。
5. 主检出完成合同门禁、Rust/前端检查与真实浏览器PWA码配对、误扫无请求、节点回归；C 由模拟原生消费方通过真实Daemon取回/验指纹/claim/status/WSS。记录“原生App真机未执行”，不得写成扫码App已交付。
