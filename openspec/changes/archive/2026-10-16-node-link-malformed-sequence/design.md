# Design

## Context

- 入站帧的唯一判定入口是 `crates/server/src/node_link/conn/wire.rs::judge`：它返回 `(Inbound, Option<u64>)`，第二个值就是「这条帧之后本连接应该期待的下一个入站序号」。`conn::session` 只消费判定结果，不自己算序号。
- 缺陷在记账口径：形状类拒绝（`Malformed` 一族、`ConnectionFieldsForbidden`）此前一律返回 `None`，于是对端**其后**一条序号正常递增的合法消息被判 `nodelink.protocol.sequence_invalid`，而它同样不推进 —— 连接退化成「只出不进」的哑管道，直到 90 秒入站静默超时才结束。
- 同构实现已在 sync 侧改对（`crates/server/src/sync/conn/wire.rs` 的 `malformed_inbound` / `sequence_after_rejection`），并且有 `sync-device-auth` 的「协议错误码与入站序号推进」要求兜底。node_link 侧既没有对应要求，也没有用例，反而有一条把错误行为写成期望的用例⑤ —— 这是缺口能长期存活的原因。
- 约束（都是既有合同，本变更不重新解释）：
  - `docs/NODE_LINK_PROTOCOL.md` §2.2：`connectionSequence` 描述**对端已发出的消息**，每个方向独立、从 `"1"` 起严格加一；重复、回退、跳号、`connectionId` 不匹配都是 `nodelink.protocol.sequence_invalid`。
  - §2.4：未知字段与未知 type 的判定必须在 **wire DTO 边界**，不能延后到 body 消费方。
  - §2.5 的三个结构上限（嵌套深度 64 / 对象字段 1024 / 数组元素 10000）由 `node_link_protocol::structure` 的**纯文本扫描器**判定，专为不复用 `serde_json` 的宽松上限而存在。

## Goals / Non-Goals

**Goals:**

- 让「每一次消息级拒绝都推进入站期望序号」，且推进与否只取决于**帧文本能不能读出本连接的下一个序号**，不取决于拒绝码属于哪一类。
- 让 node_link 的记账口径与 sync 侧同口径，消除两侧分叉。
- 用可判别的用例把口径钉住：形状错误（未登记信封字段、缺 `messageId`、结构超限、未知 type）之后，一条序号正常递增的合法消息必须被正常处理。

**Non-Goals:**

- 不改 wire 格式、schema、fixture、错误码词表；`sequence_invalid` 的**触发条件**与错误码本身不变，只是「一次拒绝之后本机记账」变了。
- 不消除结构类超限的退化（见 Decision D4）：只如实登记 + 用用例钉住边界。
- 不动 `crates/server/src/sync/**`（已修对，本变更只把它当对照口径），不改 `crates/node-link-protocol/**`。
- 不改 `docs/NODE_LINK_PROTOCOL.md`（发现的条文缺口如实登记，见文末）。

## Decisions

**D1 —— 记账判据与拒绝码解耦。** 推进与否只看「帧文本里能不能读出本连接的下一个序号」，不看拒绝码。
理由：拒绝码是对**被拒消息**的语义分类；入站序号属于**对端已发出的消息**，两者正交 —— 本机接不接受这条消息，都不改变对端已经用掉了那个序号。
备选（不采纳）：按拒绝码枚举「哪几类要推进」。这正是缺口的成因：新增一个拒绝码就要记得同步一张白名单，漏一次就退化成哑管道。

**D2 —— 读序号靠重新解析帧文本**（`sequence_after_rejection`），不复用 `Envelope::decode` 的中间结果。
理由：所有需要记账的路径都是**解码失败**路径，那时拿不到已解析的 `Envelope`（`Structure` / `Malformed` 一族 / `UnknownType` 都在 `decode` 内部失败）。
代价：被拒帧多付一次 `serde_json::from_str::<Value>`；合法帧一次都不付（只有失败分支调用它）。
备选（不采纳）：先宽松解析一次并把结果带进判定 —— 给合法路径加成本，还要把「宽松解析」与 `deny_unknown_fields` 的失败原因分开，复杂度不抵收益。

**D3 —— 推进必须四项同时成立。** 阶段是认证后、`connectionId` 与本次连接相同、`connectionSequence` 是规范十进制且 ≤ `2^63-1`、且正好等于期望值；任一不满足即**不**推进。
理由：这四项合起来才等于「对端为这条消息消耗了它的下一个序号」。认证前的消息按 §2.2 不携带连接字段，本来也没有期望序号。
这条同时是**保守方向**：重解析与真实解码若在某个边角上分叉，结果是「不推进」（保持旧行为），不会把一个读不出的序号擅自算成已消耗。

**D4 —— 结构类超限：推进口径收窄，退化不消除（已知残留）。** `sequence_after_rejection` 用 `serde_json` 重解析，它的递归上限是 128、且检查在**进入容器时先自减再判零**，因此实际能解析的是嵌套 127 层的帧；而 §2.5 的嵌套上限是 64。于是：深度 65..=127 的帧可解析（推进），**≥128 的帧即便文本合法也解析不出序号（不推进）**。
备选（不采纳）：把结构上限判定挪到解析之后 —— 违反 §2.4 的「wire DTO 边界」要求，还让超限帧先走一遍解析。
备选（不采纳）：改用不经完整解析的方式读序号（例如按文本扫描 `connectionSequence`）—— 那会改变残留的边界，属于另一个变更；本变更只在用例里钉住现状，并在 §2.5 的上限调到 128 之前不声称已消除。

**D5 —— 判定与装配留在 `wire.rs`，不引入新模块或新端口。** `conn::session` 继续只消费判定结果。
理由：本仓库已把「判定」与「判定结果产生的对端可见后果」分开（该文件模块文档首段），本次改动只调前者的一个返回口径。

## Risks / Trade-offs

- [被拒帧多付一次解析] → 只在失败分支调用，合法帧零成本；帧大小受 §2.5 与 1 MiB 单帧上限约束。
- [重解析可能与真实解码分叉] → 记账条件刻意收窄到四项可独立核对的字段（D3），分叉时的行为是不推进（保守）。
- [≥128 深度帧仍会让连接错位] → 规格的例外条款 + `wire.rs` 模块文档如实登记 + 用例钉住 127/128 边界；不声称已消除。
- [用例⑤的期望值被改向] → 它此前把错误行为写成期望；改向之后**回退修法会让它变红**，这正是要防的回归。

## Migration Plan

不涉及数据迁移、schema 变更或部署步骤：线格式、错误码、`sequence_invalid` 的触发条件都不变，改的只是「一次拒绝之后本机怎么记账」这一本机状态。回滚 = 逆向该提交；回滚后对端会重新落回「只出不进」的旧行为，无持久化副作用。

## 已知文档缺口（如实登记，本变更不顺手改）

`docs/NODE_LINK_PROTOCOL.md` §2.2 只列了 `sequence_invalid` 的**触发条件**（重复、回退、跳号、`connectionId` 不匹配），**没有**「消息级拒绝照常推进入站期望序号」这条条文；`docs/SYNC_PROTOCOL.md` 的序号章节同样只有触发条件（sync 侧的要求只存在于 `openspec/specs/sync-device-auth/`）。本变更按 tasks 1.4 的要求只登记不改：条文补齐要连规格一起动，属于权威文档自己的变更，不塞进这次修复。
