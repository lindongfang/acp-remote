# Design

## Context

现状是两笔提交：core 先做**创建提交**（会话行 + 幂等行，同一事务），再调后端启动 Agent，成功后才补写「ACP 会话标识 / 创建时目录 / 目录归属」并写终态。后端失败时以 `?` 直接冒泡——**不终结命令、不清理会话行**。实测三条失败的建会话留下三份互相否定的记录：客户端收到 `rejected`（宣称零副作用）、库里是 `accepted` 且 `session_id` 非空、重启后恢复把同一行终结为 `uncertain`。Node Link 面用「有没有持久记录」充当「会话行有没有提交」的替身，在本设计的时序下这个替身恒为真。命令面没有任何命令级日志。

## Goals / Non-Goals

**Goals:**
- 后端失败**零会话行**；命令一定到达终态，且终态类别与"Agent 侧到底有没有可能产生会话"一致。
- 判据在 Sync 与 Node Link 两面一致，不再依赖替身。
- 会话行落账前到达的事件不丢、不重、顺序正确。
- 每个被接受的命令与它的终态都有可读的结构化日志（含主体）。

**Non-Goals:**
- wire 形状不变：五态、事件形状、幂等语义不动，不新增错误码。
- 不动 `admin-state-persistence`、`storage-schema-v2-migration`、`daemon-lifecycle`（已核实：命令行形状不属前两者管辖，`owned_command.session_id` 本来就可空、无 schema 变更；启动恢复在本仓库没有任何规格要求）。
- 终态的 `details` 成因字段缓做（它是兼容新增）。

## Decisions

**D1 落账时序改为三笔：受理（只落幂等行）→ 执行 → 落账（会话行 + 回填 `session_id` + 终态）。** 备选「受理时就建会话行、失败时清理」被否：`owned_command.session_id` 是 `ON DELETE CASCADE`，删会话行会连带删掉幂等行（同 `requestId` 重发会被当成全新命令），而且崩溃窗口根本来不及清理。

**D2 窗口期事件在 broker 内有界排队，落账后按序写库再广播；超限复用既有的「超限结束该 Agent」失败关闭口径。** 备选「丢弃」会丢界面要用的 `available_commands_update` / `session_info_update`，带 id 的请求还会被回「未知会话」的错误答复；备选「在路由端排队 + core 给放行信号」需要在 core 与 agent-host 之间新增信号，而事件的写入路径本来就在 broker 手里，自足性更好。这条让「先持久化成功再广播」第一次端到端成立。

**D3 判据按「能否证明 Agent 侧未产生会话」。** 可证明（进程未能启动、Agent 明确返回错误、请求未发出）⇒ `failed`；无法证明（短请求超时、请求发出后连接断开、会话已建立但后续落盘或存储失败、崩溃窗口）⇒ `uncertain`。两个面共用；Node Link 面把「有没有持久记录」换成「会话行是否已提交」。

**D4 终态错误码复用 `internal.unavailable`，不新增错误码。** 成因由终态的 `message` 承担；机器可读的成因字段留到确有需要时再按兼容新增加。

**D5 命令级日志作为一条新要求，字段含主体标识。** 它同时承担「服务端要能看出当前由谁在控制」这一诉求，因此主体字段是必需的，而不是可选的装饰。

**D6 崩溃窗口的新形状写进 `sync-session-create` 的终态要求**，不去改 `daemon-lifecycle`（该能力没有任何恢复相关要求）。但 `docs/CORE_PORTS_AND_STORAGE.md` §6 第 22 条「恢复走**有会话**分支」必须改写——新时序下崩溃窗口的 `accepted` 行**没有**会话行。

## Risks / Trade-offs

- 这是 core 的**事务时序重构**，是本批三个变更里最重的一处；恢复路径、幂等重放、终态观察者三处都要覆盖「受理后、落账前」这一状态。
- 事件排队是新增机制，必须证明它与既有的「先提交后发布」不矛盾（排队发生在写库之前，不改变"先落库再发布"的顺序）。
- 与 `pairing-model` 同时触碰 `sync-session-create` 与 `sync-command-handling`：本变更只改「终态与幂等」与「mutation 先接受后终态」，那一个变更改授权维度与载荷形状，落在**不同的要求块**上；合入仍需串行。
