# Design

## Context

动机与用户确认要求见 [proposal.md](proposal.md)，行为规则见 `specs/session-data-lifecycle/spec.md` 与 `openspec/specs/` 长期规格。本变更当前处于需求与设计定义态，具体施工工作包与验收用例在正式开工时基于真实代码树建立。

## Goals / Non-Goals

**Goals:**
- 提供范围受控、符合单会话控制权保护、获明确授权且能力已验证的原生会话删除，确认删除后同步擦除目标展示快照并记录不含正文的最小审计。
- 分离回收无引用的平台自有缓存/临时上传、展示快照与满足收敛条件的过期核心管理元数据。

**Non-Goals:**
- 提供会话隐藏/取消隐藏；以仅删本地展示快照或直接删除厂商私有磁盘文件替代标准原生删除接口；自动清理客户端身份或撤销记录。

## Decisions

### 1. 职责与权威

只提供原生删除，原生接口未验证支持时禁用删除入口（绝不退化为仅清除展示快照伪装成删除）。外部工具直接删除的会话在显式同步重读后按原生事实呈现不存在，并同步淘汰对应本地展示快照。

### 2. 来源能力、控制权校验与固定范围接口

删除命令首先校验客户端权限与主会话控制权边界：若目标所属根主会话处于活跃加载期，发起删除者必须是当前持有该主会话控制权的客户端（未接管或由其他客户端控制时拒绝越权删除）；若主会话处于空闲未加载状态，则由受信客户端在明确固定范围确认下直接协调排他删除。命令记录确认时的原生范围、目标集合及其摘要，阻止相关新执行并协调未决审批、取消、资源释放与控制权冻结后再调用。无法限制实际影响范围的原生接口保持不可用。

### 3. 状态、快照擦除与失败

删除属于危险副作用：核心控制面受理及派发前置记录不能可靠提交时不调用原生删除；原生确认删除成功后，立即调用 `session-transcript-cache` 擦除目标及确认级联子会话的全部展示快照与分块引用，并归零运行期控制权；若原生已删除而核心管理结果或快照擦除出现局部故障，保留已知原生删除事实与待补偿清理标记并明确告警，绝不自动重发原生删除。

### 4. 自有缓存与管理元数据分离清理

只回收平台自有、无活动读取引用的临时上传分块与受管展示快照（后者遵循 `session-transcript-cache` 的 30 天滑动保留与 10 GiB 上限，绝不触碰 Harness 原生目录）。核心控制面管理元数据清理统一引用 `management-audit` 与 `session-execution` 期限策略：核对请求不可再执行、工作及审批交付已终结、未知结果核验与资源名额责任已收敛，并保留不可回退的过期拒绝依据后，再在单事务内清理到期记录。

## Risks / Trade-offs

- [部分 Harness 无标准会话删除接口] → 诚实禁用删除按钮并说明协议能力限制，不退化为隐藏或删本地文件。
- [元数据清理或快照淘汰误伤去重防线] → 核心控制面 SQLite 与独立展示快照库物理分离，严格保留请求代际与过期拒绝水位，确保清理后旧重放请求仍被确定性拒绝。

## Migration Plan

开工前盘点当时核心管理审计、请求登记表结构及独立展示快照库清理端口，增量添加删除协调状态与清理水位约束时不破坏现有身份、信任、管理记录与原生数据。
