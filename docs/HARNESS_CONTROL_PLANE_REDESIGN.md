## 1. 一页摘要

ACP Remote 的目标调整为：基于 ACP 和 Tailscale 网络路径，统一管理 Harness 的实例、会话生命周期、执行调度、状态、权限审批和审计。Harness 是实际运行任务的程序，首批重点支持 Codex、Claude Code / Claude Agent SDK、DeepSeek Harness。

已确认的核心原则：

1. **一个完整节点。** 没有中心服务器与执行节点的部署划分；管理、运行和存储都是本项目实例内部的能力。逻辑模块不等于服务或机器。
2. **不实现模型和工具系统。** Harness 负责推理、工具调用和内部任务组织；平台管理与记录其暴露的行为。
3. **原生上下文由 Harness 恢复。** 平台保存原生会话标识及必要参数，调用原生恢复接口；不通过重新发送聊天历史构造上下文。
4. **平台历史只有一个权威来源。** 数据库保存平台观察到的结构化历史、审批与管理事实，不再额外维护一份同样权威的 JSON 会话文件。
5. **实时展示与保存分开。** 流式内容先进入有界内存缓存，同时实时推送页面；合并更新数据库，结束时完成保存。
6. **会话顺序以 Harness 为准。** 单个会话内的实时、刷新、分页与重启恢复顺序一致，不按平台接收时间或内容类型重排。
7. **父子 Agent 分开展示。** 显式保存父子关系，各个会话独立保持顺序，不要求跨父子会话统一排序。
8. **允许同目录并行。** 不同会话可以同时操作同一目录，不加目录锁、不自动隔离或合并修改；同一个会话最多有一次由平台发起、尚未结束的前台执行，不限制 Harness 原生的子 Agent 或后台活动。
9. **页面断开不停止任务。** 前台执行中或等待审批时不因页面关闭、断网或资源回收策略关闭实例；仅加载但没有执行或待审批工作的资源可以按回收条件释放。
10. **不确定就明确标记。** 异常中断不自动重发输入，不假装外部副作用已经失败或成功，不复用失效审批。
11. **页面运行状态只有运行中、空闲。** 运行中表示会话资源已加载且未回收，包括等待输入；空闲表示资源已回收且会话可恢复。运行中存在有效授权请求时附加“待授权”，错误通过页面报错呈现。
12. **历史按轮次分页。** 一次用户输入及其对应执行内容为一轮，每页 20 轮；父子会话独立读取。
13. **资源按活动与容量回收。** 可安全释放的主会话 30 分钟无活动后回收；默认最多加载 50 个主会话，子会话不单独计数。创建或恢复遇到容量上限时，先回收最久未活动的可回收会话；没有候选则明确报容量已满，不取消任务、不超限、不自动排队。

## 2. 产品范围与部署边界

### 2.1 完整节点

本轮只设计一个完整节点内部的系统：

```text
Web / Mobile / CLI / IDE
            |
            v
+---------------------------------------------+
| ACP Remote                                  |
|                                             |
| Client Gateway                              |
| Identity / Policy / Approvals                |
| Harness / Session / Workspace Management     |
| Execution / Scheduler / Dispatcher           |
| History / Audit / Queries                    |
| Process Runtime / ACP Adapters / Storage     |
+---------------------------------------------+
            |
           ACP
            |
            v
Codex / Claude Code / DeepSeek Harness
            |
            v
Magpie / Models / MCP / Tools
```

Tailscale 是网络接入与部署路径，不是另一个业务节点，也不替代应用认证。未来是否管理多台机器不在本轮方案中展开，不预置中心服务器、远程执行节点或节点派发协议。

客户端形态不构成不同权限角色。首期面向个人使用，已认证且未撤销的客户端可以管理本节点；运行时权限审批单独处理。团队账号、角色和多人授权体系暂不展开。

### 2.2 管理范围

- 首期管理由平台创建的会话。
- 原生 CLI 等外部创建的会话通过显式导入接管，不自动扫描并持续双向同步全部历史。
- 平台负责 Harness 实例生命周期、会话与执行管理、调度、审批、历史展示和审计。
- 模型路由、MCP、工具实现和 Harness 内部推理不由平台重新实现；必要启动配置通过 Harness 配置引用传入。
- 思考、工具、终端、文件差异和子 Agent 等结构化内容不静默降为普通文本。
- 只能保存接入层实际暴露的内容，不能宣称恢复未暴露的内部思考或执行现场。

## 3. 逻辑模块划分

采用一个应用内的模块化结构。首期不按每个模块拆独立进程、服务或 Rust crate。

| 模块 | 职责 | 状态归属 |
|---|---|---|
| `identity` | 客户端身份、认证、信任与撤销 | 客户端身份与信任记录 |
| `policy` | 管理动作的资格判断、策略与本机限制衔接 | 策略配置；首期不引入团队角色系统 |
| `harnesses` | Harness 定义、版本、配置与实例生命周期 | 定义、实例身份与生命周期 |
| `workspaces` | 登记工作目录、解析目录引用 | 工作空间资料；不维护独占锁 |
| `sessions` | 会话生命周期、原生绑定、参与者和父子关系 | 会话、绑定、参与者与关联 |
| `execution` | Run、命令协调、排队、派发、取消与结果 | 执行和命令状态 |
| `approvals` | 请求、裁决、失效与交付跟踪 | 审批事实 |
| `history` | 会话条目、必要事件、顺序及历史查询 | 平台可恢复历史 |
| `audit` | 操作者、动作、决策依据与结果 | 审计记录 |
| `queries` | 汇总列表、过滤、分页和展示视图 | 可重建的查询结果，不决定业务状态 |

Scheduler / Dispatcher 分别表示安排执行与下发操作，放在 `execution` 内部，不单独建设远程调度服务。已有会话继续执行使用自己的原生绑定，不随机重新分配到其他 Harness。

运行与接入边界：

| 边界 | 职责 |
|---|---|
| Client Gateway | 客户端命令入口、实时订阅与分页接口 |
| ACP Facade | 按需为 ACP 客户端提供入口，与 Harness 侧适配器分开 |
| Harness Adapter | ACP 能力协商、原生会话操作、结构化事件与管理视图转换 |
| Process Runtime | 进程启停、异常检测、取消、完整进程树清理及平台实现 |
| Storage | 数据库事务、查询、附件内容与备份实现 |
| Keystore | 隔离平台密钥存储；密钥不进入普通历史字段 |

协议类型、业务对象、数据库记录和页面视图分别建模。核心业务不依赖具体数据库、网络框架、子进程 API 或 ACP DTO；适配器负责转换，应用入口负责装配。禁止巨型 Runtime 统揽所有业务。

ACP 兼容层保留管理所需的结构化视图和必要原始/扩展载荷，不能以精简内部表示替代完整协议语义。版本与可选能力必须实际协商，未来版本支持不视为已实现。

物理 crate 数量、目录名和具体存储后端可在详细设计中自主确定。之前讨论中的中心连接、执行节点和节点网关拆分不属于最终方案。

## 4. 数据对象与术语

本节是本轮重设计的概念清单，不是数据库 DDL 或最终端口签名。ID 字段表示稳定对象标识；具体类型与索引留待详细设计。

### 4.1 资源与执行对象

| 对象 | 含义 | 已讨论的主要字段 |
|---|---|---|
| `HarnessDefinition` | 一份可启动的 Harness 定义 | ID、名称、类型、程序位置、启动参数、配置引用 |
| `HarnessInstance` | 实际启动的进程实例 | ID、定义 ID、版本、适配器版本、协商能力、进程状态、启动/退出时间 |
| `Workspace` | 登记的本地工作目录 | ID、名称、规范化路径、可用状态 |
| `ClientIdentity` | 可连接本节点的客户端身份 | ID、公钥、显示名称、信任与撤销状态 |
| `Session` | 可以反复返回继续交互的会话 | ID、Harness 定义、工作空间、标题来源、来源类型、创建/活动/归档时间、当前执行引用 |
| `NativeSessionBinding` | 平台会话与 Harness 原生会话的对应关系 | 会话 ID、原生会话标识、原生存储或恢复引用、目录、配置及版本引用 |
| `Run` | 一次输入引发的执行过程 | ID、会话 ID、输入条目、执行实例、排队/开始/结束时间、状态、结束原因、原生执行标识（若有） |
| `AgentParticipant` | 主 Agent 或某个子 Agent 的稳定身份 | ID、会话 ID、直接父参与者 ID、根参与者 ID、创建 Run/工具调用引用、名称、角色、原生 Agent ID（若有） |
| `Delegation` | 一次向子 Agent 委派任务的关系 | ID、发起/目标参与者、发起 Run、输入/结果引用、原生消息或工具调用引用、状态 |

`Run` 不是一次模型请求：一次 Run 可以包含多次模型调用、工具调用和子 Agent 活动。平台不重建其内部推理步骤。

`AgentParticipant` 取代讨论中暂用的 `AgentExecution`，避免与 Run 混淆。Agent 身份不因进程重启而自动改变；恢复同一个原生子 Agent 时沿用对应身份。

### 4.2 历史、审批与内容对象

| 对象 | 含义 | 已讨论的主要字段 |
|---|---|---|
| `ConversationItem` | 一条可展示的结构化历史条目 | ID、会话内位置、Run/参与者引用、类型、正文或内容引用、完成状态、内容版本 |
| `SessionEvent` | 必须保留的状态变化及关联事实 | ID、会话内位置、事件类型、Run/条目/工具/审批引用、必要协议载荷及来源 |
| `ToolCall` | 平台观察到的一次工具执行 | ID、原生调用 ID、会话/Run、名称、类别、输入、输出、状态、错误、审批/附件引用 |
| `ApprovalRequest` | Harness 请求批准的具体操作 | ID、会话/Run/工具引用、原生请求与运行连接标识、操作内容、可选决定、有效状态 |
| `ApprovalDecision` | 用户作出的最终裁决 | 请求 ID、决定、决定者、时间 |
| `ApprovalDelivery` | 裁决是否成功交付到有效的 Harness 请求 | 请求/裁决引用、交付状态、失败原因 |
| `Command` | 可追踪的管理请求 | ID、稳定请求标识、调用客户端、动作、目标、受理与结果状态 |
| `Blob` | 按引用读取的大块内容 | ID或内容摘要、字节大小、媒体类型、内容位置、引用关系 |
| `AuditRecord` | 谁要求做什么、依据与结果 | ID、操作者、动作、目标、时间、决策依据、相关命令/事件引用 |

Blob 适用于图片、大型输出等，不是另一份会话正文文件。工具调用是历史对象，不代表平台建设工具目录或工具执行系统。

### 4.3 关联约束

1. 一个 Harness 定义可以有多个运行实例、多个会话；实例退出不删除会话。
2. 一个会话可以有多个 Run，但同时最多一个由平台发起、尚未结束的前台执行；此时再次提交普通输入明确返回忙碌，不默认排队。这不禁止 Harness 内部的子 Agent、后台任务或原生并行活动。
3. 同一目录可以关联多个会话，允许并行修改，不加独占约束。
4. 原生会话绑定用于恢复原会话；恢复失败不能静默创建一个新原生会话替代。
5. 父子关系显式记录在 AgentParticipant 中：根参与者没有父参与者；父关系不能形成循环，子参与者必须能追溯到根。
6. 子 Agent 有可靠独立会话身份时使用独立 Session 保存历史。父会话只保存实际收到的委派输入、返回和关系，不复制整份子会话历史。
7. 父子归属说明谁创建谁；Delegation 说明哪次任务委派给谁。同一子 Agent 可以被多次委派，不能把每次委派误认为创建新 Agent。
8. Harness 未提供可靠子身份或父子关系时，保留已知信息并明确缺失，不伪造执行树；只有工具调用时保留为工具调用。
9. 审批请求最多有一个最终裁决；裁决保存与交付成功分别记录。旧运行连接中的失效请求不能因恢复而重新变成有效审批。
10. 原生标识按 Harness 与原生存储范围解释，不能假设三款 Harness 的标识全局唯一或平台 ID 与原生 ID 天然相同。

父子会话分别展示，可从父会话跳转子会话，并展示名称、角色和状态；不在一条时间线上混排父子正文。

### 4.4 字段与记录职责的补充

对象字段按上述清单收敛，具体类型、可空性、数据库列和索引可自主细化。以下职责必须保持：

- 平台 ID 与原生 ID 分别保存；原生绑定包含 Harness 及原生存储范围。平台不能将同一范围内的同一原生会话重复登记成两个可同时写入的会话。
- ConversationItem 保存稳定条目 ID、会话内位置、所属轮次/Run、参与者、类型、内容版本与完整性。位置与版本分别表达“在哪里”和“哪次更新”，不能混用。
- 工具卡片的位置属于 ConversationItem，工具结构化输入、输出与结果属于 ToolCall；卡片引用工具对象，不再独立维护一份可修改的工具正文。审批卡片同理。
- Command 保存请求标识、调用客户端、动作、目标、请求摘要和处理结果；相同请求标识重试返回原处理结果，内容不一致则明确报错。平台请求标识不等于 ACP JSON-RPC 请求 ID。
- Run、条目、工具和审批的所属会话引用必须一致，不能跨会话串联。Delegation 是显式跨父子会话关系，不受此处同会话引用限制。
- 工作目录暂时不可用不自动删除 Workspace；恢复同一个原生 Agent 不自动创建新的 AgentParticipant。
- 凭据和密钥保存为安全引用，不进入普通正文、配置快照或审计载荷。

### 4.5 平台约束与 ACP 原生流程

平台可以强制自己的关联一致性、请求防重复、审批唯一裁决和命令协调，但不能为凑平台状态而重新解释 Harness 流程。

“取消中仍占用名额”仅指：在确认前台执行结束前，不向同一个原生会话派发下一次普通输入。它不是消息位置、目录锁，也不要求退出整个进程或结束所有原生后台任务。

执行结束、取消和权限请求首先遵循实际协商的 ACP 版本。以 ACP v1 为例：

- 前台轮次结束由原 `session/prompt` 响应及结束原因表达。
- `session/cancel` 是通知，没有独立成功响应；发送通知不等于取消完成。Agent 中止相关操作并发送剩余更新后，应对原 prompt 返回 `cancelled`。
- `session/request_permission` 是请求/响应；取消当前轮次时，客户端必须将相关待处理权限请求回复为 `cancelled`。
- 取消未确认或连接丢失时，不假装取消完成，也不盲目重发原输入；按已知事实记录中断或结果未知。

其他版本按对应规范映射，不把 v1 的完成信号套用到其他版本。三款 Harness 的验证是接入验收：核对适配器是否正确处理规范消息及已协商能力，不重新决定协议已定义的语义，也不要求 Harness 遵循平台自造的流程。

规范来源：[ACP v1 执行与取消](https://agentclientprotocol.com/protocol/v1/prompt-turn)、[权限请求](https://agentclientprotocol.com/protocol/v1/tool-calls)。

## 5. 存储权威与历史保存

### 5.1 同一事实只有一个权威来源

| 事实 | 权威来源 |
|---|---|
| Harness 下次如何继续原上下文 | Harness 原生会话存储 |
| 页面曾经收到的可恢复内容与顺序 | 平台数据库中已提交的条目和必要事件 |
| 操作者、审批裁决、管理命令结果 | 平台数据库 |
| 图片等大块内容的字节 | 数据库引用的内容存储 |
| 当前进程、工具是否仍在执行 | 当前运行实例的实际观测；未知则显式标记 |

原生会话存储与平台历史职责不同，不互相覆盖，不持续合并扫描。不通过解析和改写 Harness 私有会话文件实现日常恢复。

数据库内可按用途建立关联表和查询投影，但同一事实不能有两个可独立修改的权威副本。查询投影是为读取整理的数据，可以从规范记录重建。

### 5.2 最终保存模型

**正文按条目保存，必要状态变化按事件保存。** 这替代本轮早期“所有原始流式事件永久追加、正文完全从事件重建”的候选方案。

- 一条连续回复条目只保留一条逻辑正文记录，流式到来时更新它。
- 一次执行可以包含思考、文字说明、工具调用、文字结论等多个不同条目，不能合成一段回复。
- 同一条目可以有内部内容块或附件引用；这不等于每个字或每个协议分片都是永久消息。
- 思考与工具等条目之间的顺序不能被后续正文合并破坏；文字跨过工具或其他可见条目后不能回填到前面的文字条目。
- 文字增量不逐条永久保存，不承诺回放逐字生成速度；历史恢复的是内容、结构、实际可证明的顺序及必要状态变化。
- 最终结果更新原条目，不能再次插入一条相同消息；若协议最终值是替换而非追加，适配器必须按实际语义处理。
- 原始/扩展载荷的保真与文字分片永久留存是不同要求；需要保留的结构化字段不能因正文合并而被丢弃或经有损数值转换。

### 5.3 实时输出、缓存与入库

```text
Harness ordered output
          |
          v
Adapter: assign item identity and source order
          |
          v
Bounded in-memory accumulation
          |
          +----> immediate stream to clients
          |
          +----> merged database updates
```

已确认起始参数：每 **500 毫秒**或累计 **64 KiB** 待保存增量，先满足者触发保存；条目结束、执行结束和正常释放时立即完成相应保存。缓存必须有界，具体计算范围、调优参数与配置键在详细设计中确定。

页面保持实时流式输出，不等待数据库事务，不以 500 毫秒保存周期批量展示正文。渲染内部可以优化，但不能把保存节奏强加给输出体验。

同一条目的更新按内容版本串行提交，不能让较旧的异步写入覆盖较新正文。有关联的状态变化、必要事件与命令处理结果应在同一事务中提交，避免部分成功。

**已接受的代价：** 页面可以先显示未保存内容。进程异常退出或掉电时，最后少量已显示但未提交内容可能丢失。500 毫秒是正常工作时的触发目标，不是磁盘卡顿或故障下的严格损失上限。

实时连接断开后以数据库中的已保存版本重新读取；不能让客户端把未保存片段当作永久恢复位置。具体客户端版本对齐和断线衔接协议在详细设计中补齐。

### 5.4 保存失败

- 明确提示“历史保存失败”，不能把未保存的结果显示成已可靠保存。
- 有限缓存并重试；持续失败或达到缓存上限时停止继续执行，不能无限增长内存。
- 停止接纳新执行，并请求 Harness 取消或结束当前工作；不能声称取消一定回滚已有副作用。
- 未确认结束的工具、进程和 Run 保持待核实或结果未知，不伪造成功。
- 具体重试、内存上限及停止阈值属于实现前需补齐的参数，不再扩大为用户需求访谈。

### 5.5 事件、正文与审计的区别

必要事件记录执行开始/结束、审批请求/裁决/交付、工具状态变化、Agent 创建/委派、上下文压缩与异常恢复等事实，不复制一份完整正文。

ConversationItem 和 ToolCall 保存各自内容及当前已提交状态；SessionEvent 引用这些对象。审计记录操作者和决策依据，引用业务对象，不再复制完整 prompt、工具输出或协议认证数据。

具体事件词表、字段和重建范围在详细设计中明确，不能声称未保存的逐字增量仍可从事件重建。

### 5.6 输入受理、终态与异常恢复

1. 平台检查身份、会话可执行条件与请求标识。
2. 在单次事务中保存已接受命令、用户输入及其 Run，再确认受理，随后向 Harness 派发；“已接受”不代表 Harness 已执行。
3. 派发结果不明确时进入结果未知，不自动重新派发。原生恢复不能替代副作用确认。
4. 输出沿 §5.3 的实时/保存两条路径推进；条目结束立即保存最终值，不重复插入最终消息。
5. 收到执行结束后，先保存剩余正文，再原子提交 Run 终态与必要事件；最终成功不能先于相关正文可靠保存。
6. 异常重启保留已提交内容，将残留未完成条目标记为中断，将原连接的审批请求失效，并根据证据收敛 Run 结果；不能补写未观测到的成功。

每次用户输入对应的历史轮次应有稳定身份和顺序；自动重试不增加第二轮。历史轮次与原生执行的关联根据实际来源保留，不能为外部导入历史伪造已执行事实。

## 6. 顺序与分页

### 6.1 会话执行顺序

**页面必须按照 Harness 会话实际输出/执行的可观察顺序展示，不能用平台接收时间猜测。**

1. Harness 提供原生顺序标识时，适配器按其语义使用和验证。
2. 只有有序输出流时，在读取入口固定该会话的顺序；后续异步解析、附件读取、写入和页面更新不得改变顺序。
3. 条目首次出现时固定位置，之后的流式更新不改变位置。
4. 不按思考、工具、文字等类型重新排列，不跨其他可见条目合并文字。
5. 时间戳只作辅助显示，不作权威排序键。
6. Harness 历史读取与实时输出必须证明排序一致；不能证明时不能宣称满足严格顺序要求。
7. 父子会话独立展示、独立排序，不要求或伪造跨会话全局执行顺序。

适配器未暴露的真实内部步骤无法还原；排序承诺针对其实际暴露的会话内容，不把平台观测冒充未暴露的内部事实。

思考、文字、工具等共用同一会话的顺序空间，是为了保留实际交替关系，而非按类型分别排序。条目身份与位置在异步处理前确定：例如“思考 → 文字说明 → 工具调用 → 文字结论”，即使工具内容保存较慢，也不能与后面的文字交换位置。工具后续输出和完成状态更新原工具条目；之后产生的新文字或思考使用后续条目，不回填跨越的旧条目。

已分配给实时条目的位置不能在异常重启后复用，具体分配机制可自主设计；位置允许空缺，不要求无间断连续。条目首次位置、内容版本和已保存版本分别管理，不能仅靠最新位置识别所有更新。

### 6.2 历史分页

**已确认：一次用户输入及其对应执行内容为一轮，每页 20 轮。** 当前正在执行的一轮也计入。每轮包含对应输入、思考、回复、工具、审批等条目；不因条目数量多而把一轮切到相邻页。

分页是前端展示与按需加载需求，不是 Harness 能力，也不是把数据库中的会话正文按页存成文件：

- 数据库保存完整历史与稳定轮次关联。
- 后端根据前端请求按段读取，不先读取、传输全部历史再由前端隐藏大部分。
- 前端首次读取最近 20 轮，向上滚动再请求更早的 20 轮，各页及页间始终保持 Harness 会话顺序。
- 使用稳定轮次边界作为游标；游标表示从哪轮继续读取，不依赖会随实时新增改变的行数偏移。
- 父子会话独立分页，子 Agent 正文不计入父会话的 20 轮。
- 超大工具输出、附件可以按需展开，不得因此静默漏掉该轮条目。
- 初次打开页面时必须衔接当前内存中的实时内容，不能只展示已保存部分、等下个增量才补出当前回复。
- 正在生成的条目沿用原位置和 ID，以内容版本更新，不新增轮次、不移动位置。旧版本不能覆盖新版本。
- 同一工具条目可能在后面的输出出现后才完成，因此同步必须覆盖旧位置上的更新，不能只订阅“最新位置之后”。
- 分页结果与实时更新按稳定身份及版本衔接；这是更新同一对象，不是按文字相同去重。
- 已显示版本与已提交版本分开；重连以数据库为基线，按 §5.3 处理仍存在的实时缓存或已丢失的未保存尾部。

具体游标编码、版本字段、原子读取/订阅衔接和响应字节预算可自主细化，不改变每页 20 轮的产品规则，也不恢复为按条目数分页。

### 6.3 历史读取、上下文恢复与重放

| 行为 | 读取来源 | 是否启动/恢复 Harness |
|---|---|---|
| 页面查看、刷新、翻页 | 平台数据库 | 否 |
| 继续原会话执行 | 原生绑定及 Harness 原生存储 | 是，按需恢复 |
| 显式导入外部会话 | Harness 支持的历史接口等 | 按适配器能力 |
| Harness 历史重放 | Harness 将旧消息再次发出 | 仅在需要的加载路径发生 |

正常恢复优先调用不重放历史的接口。若适配器只能使用带重放的路径，必须隔离旧历史与新输出，不能把重放当成新回复；具体关联方法由适配器验证。

不按相同文字、时间接近或内容摘要判断两条消息相同。无法可靠关联的外部历史不能宣称可以无损自动去重。

## 7. 生命周期与多客户端行为

### 7.1 页面运行状态与内部操作分开

页面会话运行状态固定为：

| 展示 | 定义 |
|---|---|
| 运行中 | 会话资源已加载且尚未回收，包括正在执行和等待下一次输入 |
| 空闲 | 会话资源已回收，平台历史与原生绑定保留，可以恢复会话 |
| 运行中 · 待授权 | 运行中的特殊展示，存在有效待处理授权请求，不是第三个独立生命周期 |

一轮回复完成，只要运行资源未回收，仍为“运行中”，不能显示为空闲。空闲指资源已回收，不等于 ACP 原生的“当前前台没有工作”。恢复中可以给出操作加载反馈，连接异常、恢复失败等以页面报错呈现，不新增会话运行状态，也不能用空闲掩盖未知资源情况。

内部仅保留执行协调与历史解释所需的信息，不把每个瞬时步骤都升级成会话字段或页面状态：

| 对象 | 内部记录职责 |
|---|---|
| Session | 原生绑定、归档时间等；页面活动状态由实际资源事实推导，不维护庞大生命周期枚举 |
| 加载/释放/删除操作 | 由 Command 跟踪进行过程与结果；不要求持久化“删除中、已删除”会话状态 |
| HarnessInstance | 进程存活、退出时间与原因，启动/停止过程由操作管理 |
| Run | 执行进行情况与完成、取消、失败、中断、结果未知等终态；取消中不等于已结束 |
| ConversationItem | 生成是否完整；异常时标记中断，不意味着任务本身成功或失败 |
| ToolCall | Harness 实际提供的运行及结果信息，未确认结果不补成成功 |
| Approval | 请求是否有效、唯一裁决、交付结果分别记录 |

正常资源转换是“空闲 → 恢复成功 → 运行中”和“运行中 → 确认释放 → 空闲”。恢复失败、释放失败或连接异常通过操作结果及报错表达，不假装状态已成功转换。

Run 按 ACP 前台执行语义由已接受、派发/执行推进到终态；取消请求不直接结束 Run，收到对应完成信号后才能解除前台执行约束。新一轮建立新 Run，不让已结束 Run 重新变为运行中。会话资源状态不能替代某轮结果：同样处于运行中的会话，上一轮可能完成，也可能失败。

普通删除完成后不必为展示“已删除”保留会话记录。重复请求处理和必要审计使用 Command/AuditRecord 保存删除事实，不把它作为可见会话继续返回。完整内部状态枚举和合法转换可自主补齐，但不得额外扩大页面状态。

### 7.2 断开、释放、恢复、删除

| 操作 | 已确认行为 |
|---|---|
| 页面关闭或客户端断网 | 后台执行与 ACP 保持，不因没有页面而中止任务 |
| 自动资源回收 | 只回收没有执行、待审批或需保留后台工作、满足 §7.4 条件的资源；回收成功后页面才变为“空闲” |
| 显式释放 | 阻止新的相关操作，协调结束工作，按实际能力关闭并释放；失败明确反馈，不假装成功 |
| 恢复 | 使用原生标识与参数，成功后才接受新输入；不自行灌历史 |
| 异常退出 | 保留已提交历史，标记中断或结果未知；不自动重发输入 |
| 普通删除 | 删除平台记录及不再被引用的附件；不默认为删除原生会话 |
| 删除原生会话 | 独立选项，必须验证对应 Harness 支持，不能承诺统一可用 |

正常释放应完成缓存保存；无法保存时按保存失败处理。历史恢复不等于恢复文件系统快照，也不保证外部工具、终端或子 Agent 从原执行指令位置续跑。

### 7.3 多客户端与原生 CLI

- 多个网页、手机或平台 CLI 可以同时查看和操作同一会话。
- 经过平台的命令统一协调；同一会话存在未结束的前台执行时，新普通输入返回忙碌，取消和有效审批仍可处理。这与页面“运行中”（资源已加载）不是同一个判断。
- 多客户端同时裁决审批，最多接受一个最终决定；交付失败独立记录。
- 平台内部的锁只能约束平台操作，不能强制阻止外部原生 CLI 打开同一原生会话。
- 提供释放入口方便切换原生客户端；重新接管后的上下文恢复仍交给 Harness。
- Harness 有可靠占用检测时呈现占用状态；没有时明确能力限制，不承诺平台可以检测所有外部写入。
- 不支持承诺外部 CLI 与平台同时写同一原生会话的一致性；这与多个会话共享目录并行是不同问题。
- 原生 CLI 操作期间新增历史是否补采属于显式导入/接管设计，不承诺自动同步完整外部历史。

### 7.4 自动资源回收与容量上限

本节规定平台何时发起自动回收。ACP 提供关闭与释放机制，不替平台决定 30 分钟超时或容量上限；这些是本轮已确认的产品策略，不是现有配置已实现的声明。

#### 7.4.1 计数与可回收条件

- 默认最多同时加载 **50 个主会话**，不是最多保存 50 个历史会话，也不是最多运行 50 个 Harness 进程。
- 子会话不单独占用这个名额；其资源和活动归属于对应主会话的执行树。子会话不计数不意味着不消耗内存或进程资源。
- 新建并加载主会话、恢复已回收的主会话都需要名额；查看历史不需要，已经加载的会话不重复计数。
- 前台执行、有效待授权请求、需要保留的后台工作，以及子 Agent 的上述活动，均阻止对应主会话被自动回收。没有可靠证据证明可安全释放时，不能当作候选强制关闭。
- 释放某个会话不等于关闭整个 Harness 进程；共享实例不能因回收一个会话影响其他会话。

#### 7.4.2 30 分钟计时

“没有消息”按**没有会话活动**解释，包含主会话及所属子会话的用户输入、Harness 回复、可见思考、工具进展和子 Agent 活动。它们刷新活动时间；网络心跳、页面打开、查看历史和翻页不刷新。

只有执行、审批及需要保留的后台工作全部结束，主会话可以安全释放后，才开始计算无活动时间。计时起点不得早于进入可回收状态的时刻；之后发生新的有效会话活动则重新计时。刚加载但尚未输入的会话从加载成功且满足可回收条件时开始计时。

可回收状态持续 **30 分钟**且没有新活动时发起回收。长工具调用或等待审批即使超过 30 分钟也不自动中止；工作结束后重新开始计时，不因上条文字消息很早就立即回收。

用户正在查看页面也不保活。资源回收后历史继续可读，页面状态变为“空闲”；下一次输入按原生绑定恢复会话后执行。

#### 7.4.3 容量满时优先回收

创建或恢复主会话需要新增名额时：

1. 未达到 50 个时正常加载，分配过程需协调并发，不能因多个客户端同时请求而超限。
2. 达到上限时，在可安全释放的候选中，选择**最久没有会话活动**的主会话。容量触发不必等待满 30 分钟。
3. 在关闭前重新确认候选没有新输入、授权或后台/子 Agent 活动，并完成待保存内容的刷新。
4. 按已协商能力调用关闭/释放路径，确认资源释放成功后才释放名额，再创建或恢复目标会话。
5. 释放失败不得假装已有名额；按实际结果处理并给出明确错误，不静默超限。
6. 没有可回收候选（例如全部忙碌）时，明确提示容量已满，不强制取消任务，也不自动排队。

计数范围、回收资格和名额预留是平台内部规则，不增加新的页面会话状态。仅发出关闭请求、连接异常或进程状态未知都不能直接视为成功回收。

#### 7.4.4 待实施参数与验收

30 分钟与 50 个是已确认的默认值。具体配置键和调度扫描方式可自主确定，正式实施时同步配置权威文档，不在本次整理中新增配置接口。

验收应覆盖：超时边界、新活动重置、长任务与待授权保护、子会话/后台活动保护、查看不保活、容量触发提前回收、最久未活动选择、并发创建不超限、关闭失败不释放名额，以及满额无候选时明确拒绝。

## 8. 保留、附件、删除与备份

- 默认不自动清理平台历史；不沿用旧合同中的保留窗口来静默删除新方案的历史。
- 记录接入层实际暴露的回复、可见思考、工具、子 Agent 与审批，不声称完整记录 Harness 未暴露的内部行为。
- 超限、缺失或未提供的内容明确标记，不能静默裁剪后声称完整恢复。
- 大块内容通过摘要和引用保存；同内容可复用字节，消息本身不能据此被去重。
- 删除会话后，只回收确认没有其他引用的内容；父子会话级联删除、审计保留与进行中删除的完整规则在详细设计中补齐。
- 备份区分平台数据库、附件和 Harness 原生存储。只备份平台历史不能承诺恢复原生上下文；只备份原生存储也不能承诺恢复平台审批与审计。
- 一致性备份、恢复检查与故障处理在实施前设计，不通过简单复制若干正在写入的文件声称备份成功。

## 9. 三款 Harness 调研结论与证据

| Harness | 本轮发现 | 对设计的含义 |

## 10. 实施前的设计与验收工作

### 10.1 可自主补齐的详细设计

本轮产品方向足够进入设计整理，无需逐字段向用户确认。实现前应补齐：

- 对象完整字段、来源标识、关系约束和生命周期。
- 每个状态的合法转换、错误与异常恢复。
- 条目身份、流式边界、顺序验证和最终值更新规则。
- 缓存范围、内存上限、保存失败重试与停止阈值。
- 事务边界、命令重复处理及审批交付规则。
- 实时内容版本、已保存位置与历史分页的衔接。
- 显式导入/接管、删除、附件回收及备份恢复规则。
- 数据库表结构、索引、迁移与容量测试。

这些由后续设计自主确定；若发现必须改变已确认用户行为、安全边界或数据权威，再明确指出影响并确认。

### 10.2 必须实测的能力

至少对三款 Harness 的固定版本验证：

1. 正常结束后释放进程，再恢复原会话并继续输入，上下文连续。
2. 页面断开不停止 Harness，重新连接后恢复平台历史与当前输出。
3. 工具执行中异常退出，平台不自动重发，保留可证明事实并标记未知部分。
4. 等待审批时异常退出，旧请求不被复用，多客户端不能产生多个最终裁决。
5. 子 Agent 身份、父子关系和各自历史可恢复；没有暴露的能力明确标记。
6. 实时、刷新、分页、重启后的同一会话顺序一致；思考、工具和文字交替不被合并重排。
7. 上下文压缩不导致平台已有完整历史被摘要覆盖。
8. 高速输出与长会话下保存和分页可用，页面仍实时输出，缓存保持有界。
9. 保存失败可见、停止策略有效；验证已接受的尾部未保存内容损失，不声称零丢失。
10. 释放失败、外部占用与不支持接口明确呈现，不以假成功掩盖。
11. 按 §7.4 验证 30 分钟回收与默认 50 个主会话上限，活动保护、候选选择、释放确认和并发名额协调均符合已确认策略。
