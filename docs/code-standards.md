# Code Standards

本文件收录从 [LESSONS.md](../LESSONS.md) 晋升来的硬规则。审查前必须逐条对照。

同一规则在三次不同事件中出现后晋升。晋升时同步从 [LESSONS.md](../LESSONS.md) 删除原条目，只在本文件保留正式规则；晋升后再次发生同类问题时，只更新本文件的对应规则和复发记录，不得重新写回 LESSONS。

## 硬规则

1. **核心变更合并前执行 Red Check**：针对**产品缺陷修复**以及**核心安全、协议语义、并发/状态机不变量**的新增测试，必须在修复前（或针对旧行为）观察到断言失败，再在新实现下通过，证明测试对真实行为有约束力。测试运行器脚本、夹具脚手架、纯结构/类型重构与文档变更免除“写完后再人为改坏代码造 Red 日志”的形式化退化留证。
2. **未跑的检查必须明确列出**：不得以计划、模拟结果或结构通过冒充执行。交付摘要逐项区分 `passed` / `failed` / `not-run`，`not-run` 如实说明原因。
3. **正式验收与审查绑定 Git Commit**：集成门禁的验收与审查统一绑定本地工作分支的具体 `commit SHA`（`git rev-parse HEAD`，且受跟踪文件 `git status` 干净；PR 合并至 `main` 时走 squash merge）。废除未提交工作区的多文件手工 SHA-256 清单快照与源码副本入库。期间产生新代码修复 commit 时，按 `git diff <old-sha>..<new-sha>` 评估影响范围并做增量重验/复核；门禁通过后仅回填 `plan.md` 结果、勾选 `tasks.md`、同步 `openspec/specs/` 与 `testing/suites/` 及归档的纯文档提交，只要 `git diff <tested-sha>..HEAD` 不含任何产品/测试代码及构建配置改动，直接继承 `<tested-sha>` 结论，不重跑验收或审查循环。
4. **同一工具调用意图最多两次，等待型轮询最多一次静默等待**：查询意图按工具名、会话/资源身份、规范化参数和所需判断识别，不按命令字符串识别。等待型调用中，只有新增 stdout/stderr、退出码出现、进程状态变化、目标文件变化或资源身份变化才算进展；调用完成但仍返回“运行中”不算进展。长任务应一次等待到工具允许的上限，不得用多个短超时轮询累积等待时间。查询型调用第二次仍未产生改变判断的新信息时，第三次不得重复调用；等待型调用第一次仍无进展时只记录“仍在运行”，第二次仍无进展必须停止同一 session 的原样轮询，下一步只能改用一次实质不同的证据查询，或明确报告任务仍在运行并结束本轮。结果已经足以回答当前问题或任务仍在后台运行时，不得用同类轮询假装继续推进。
